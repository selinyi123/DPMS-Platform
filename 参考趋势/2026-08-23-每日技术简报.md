# 每日技术简报｜2026-08-23

## 今日结论

今天最值得追踪的不是新模型，而是 Agent Runtime 的两个基础能力正在快速成熟：

1. **Runtime Event Log / durable authority**：执行日志不再只是观测数据，而开始成为 session、恢复、UI、上下文投影和审计的权威来源。
2. **Cost / cache / budget engineering**：缓存命中、cache write/read、token、tool-call 上限和 per-run spending 正逐渐成为 Agent 配置的一部分，而不是账单后的统计。

对 DPMS / PPE / KIS / ClipVault / Binggo 的共同启示是：下一阶段最值得共享的 primitive 不应继续扩成新的 Agent 协议，而应围绕 `ExecutionRecord / ContextRef / CostProfile / PolicyDecision / Evidence` 建模。

## 2. 今天最值得看的开源项目

### Apache Maka

GitHub： https://github.com/apache/maka

Maka 是今天优先级最高的架构参考之一。它的核心表述是：

> Log is the Runtime.

模型消息、Tool Call、Tool Result、permission decision、termination fact 都进入 Runtime Event Log；Session、UI、Context、Recovery 则是对该日志的投影。

值得借鉴的架构是：

```text
Runtime Host
   ↓
AgentRun
   ↓
Runtime Event Log   ← operational authority
   ↓
┌──────────┬──────────┬──────────┐
Session    UI       Context    Recovery
projection projection projection projection
```

Maka 还明确区分“Context”和“History”：Tool Result pruning、LLM compaction 可以改变下一次 inference 看见什么，但不会销毁执行证据。

这对 DPMS 和 KIS 都非常重要。

### Vercel Labs / fx

GitHub： https://github.com/vercel-labs/fx

`fx` 是 Zig 写的极小型 coding-agent harness，重点不是功能最多，而是 **embeddability**：CLI、本地/云模型、Skills、MCP、subagents，核心还能通过 WASM 嵌入其他宿主。

近期 PR 很有参考价值：

- permission mode 必须保持一致；
- destructive action 不进入 automatic review；
- completed one-off subagent session 要及时退休；
- connection/authentication ownership 要显式化；
- persistent goal tracking；
- MCP 启动 timeout。

这些都说明生产 Agent Harness 的难点越来越集中在生命周期、权限、认证和恢复，而不是 ReAct loop。

### Apache Maka 的 Windows AppContainer sandbox

Maka 0.1.11 还加入 brokered Windows AppContainer sandbox，并强化 IPC ownership / ACL。

这个点对以 Windows 为主的本地产品尤其值得看：多数 Agent sandbox 设计仍然 Linux-first，而 Windows 原生隔离层仍是明显缺口。

## 3. 可借鉴的技术趋势与架构参考

### 趋势 A：Event Log 正在从 observability 变成 state authority

传统系统常见：

```text
DB state = authority
logs = debugging
```

Agent Runtime 越来越适合：

```text
append-only execution facts
        ↓
state projection
        ↓
UI / recovery / audit / context
```

这样最直接的收益是：

- session 恢复有事实依据；
- UI 不需要自己猜 Agent 当前状态；
- Tool side effect 可以有明确生命周期；
- context compaction 不会删除 evidence；
- replay / audit 能够基于稳定事实重建。

但不能机械套用 event sourcing。外部不可逆 side effect 仍必须有 reconciliation 状态；不能因为日志里没有 success 就自动重试。

### 趋势 B：Context、History、Evidence 必须拆开

建议统一为三层：

```text
Evidence
→ 永久执行事实，不因 token budget 删除

History
→ 用户/系统可浏览的交互记录

Context
→ 当前 inference 实际注入的有限工作集
```

这是 KIS 与 DPMS 可以直接共享的语义边界。

### 趋势 C：Cost Profile 应成为 Agent Configuration 的一级维度

未来评估一个 Agent，不应只写：

```text
model = X
prompt = Y
```

而应至少绑定：

```text
ModelConfig
PromptRevision
ContextPolicy
CachePolicy
ToolPolicy
ExecutionBudget
```

然后记录：

```text
success
quality
uncached_input
cache_write
cache_read
output_tokens
tool_calls
wall_time
cost
```

这会直接影响 PPE 的产品边界。

## 4. 对五个项目的机会、风险和行动建议

### DPMS

当前 DPMS 已经具有复杂的 Outbox、Redis continuity、platform lane、real-run gate、Worker identity、evidence 和 policy 基础。现在不建议为了追 Agent 热点再建立第二套 Runtime authority。

建议新增一个**只读 Execution Projection Layer**，从现有 DB/event/audit/evidence 产生统一 `ExecutionRecord`：

```text
ExecutionRecord
├ execution_id
├ platform
├ task_id
├ actor
├ state
├ tool/action facts
├ policy decisions
├ evidence refs
├ cost/resource facts
└ reconciliation state
```

重点是“投影现有事实”，不是替换现有 real-run 闭环。

机会：以后 Agent UI、协作 Session、PPE Eval 都可以消费同一个投影。

风险：不要把外部平台动作做成通用 replayable event；点赞、关注、转发等 side effect 必须继续由现有幂等/回读/reconciliation 逻辑治理。

### Prompt Performance Engine

PPE 当前已经有严格 benchmark、receipt verifier、Docker sandbox、replicate aggregation 和 authority gate。今天最值得新增的不是更多 Prompt 生成策略，而是 **Cost/Cache Experiment**。

建议增加：

```text
CostProfile
├ uncached_input_tokens
├ cache_write_tokens
├ cache_read_tokens
├ output_tokens
├ tool_calls
├ wall_time
└ estimated_cost
```

并允许同一 benchmark 做：

```text
CachePolicy A/B
Budget Sweep
Context Layout Ablation
```

最终输出 `quality × reliability × cost` Pareto frontier。

风险：不能把 provider 自报 usage 当 authority evidence；应保持现有“self-reported metadata ≠ independent authority”的纪律。

### KIS

KIS 当前 canonical/derived 分离和人工确认队列方向是正确的。今天最值得吸收 Maka 的不是“把所有东西写成日志”，而是：

> Context 不是 History。

建议新增 `ContextSelection` artifact：

```text
ContextSelection
├ task/session id
├ selected card ids
├ exact revisions/content hashes
├ selection reason
├ token budget
├ trust state
└ generated_at
```

这样以后 Agent 回答错误时，可以明确判断“知识不存在 / 检索没选中 / 选中了但模型没用对”。

风险：不要把 Runtime Event Log 和 KIS Knowledge Store 合并。前者是执行事实，后者是知识资产，生命周期和信任语义不同。

### ClipVault

今天没有发现足够强的新竞品信号支持扩大 ClipVault 的功能边界。

真正值得做的是继续保持 local-first，并为未来本地 Agent / Context Bridge 预留：

```text
origin
source_app
content_hash
sensitivity
persistence_policy
session_ref
```

尤其 OTP、credential、secret 必须继续与普通 history / knowledge path 隔离。

机会：Windows 原生 sandbox / AppContainer 生态正在变得更值得研究，未来如果 ClipVault 引入本地 AI classifier，可考虑把 classifier 运行隔离也纳入 threat model。

### Binggo

Binggo 已经有 scheduler、job state machine、local API、MCP 和确定性 B 站动作链，是最适合快速验证“Agent Control Surface”的项目。

今天建议比昨天再向前一步：建立只读 `Run Trace` API，把现有 job/actions/scheduler 的执行事实统一输出：

```text
GET /api/runs/{id}/trace
```

至少返回：

```text
state transitions
action attempts
retry/backoff
risk decisions
external response class
evidence refs
```

这样 MCP Agent 可以先做：

```text
inspect → explain → preview
```

而不是直接扩大写权限。

风险：不要让 LLM 根据聊天上下文直接决定点赞/关注/转发；Agent 只生成 Action Preview，真实动作继续经过现有确定性 executor 与风控。

## 5. 今天建议真正执行的四项工作

1. **DPMS**：设计 `ExecutionRecord v0.1`，只做 existing facts 的 projection，不改变 real-run authority。
2. **PPE**：增加 `CostProfile + CachePolicy` schema，并做一次缓存布局 A/B benchmark PoC。
3. **KIS**：增加 `ContextSelection` artifact，记录“本次 inference 到底用了哪些知识版本”。
4. **Binggo**：新增只读 Run Trace / Action Preview；ClipVault 暂不扩功能。

## 今日最终判断

过去一周我们一直在增加：

```text
MemoryBudget
PolicyDecision
ExecutionBudget
TrustContext
ExecutionSession
```

今天最值得补的不是第六个控制对象，而是一个更基础的事实对象：

```text
ExecutionRecord
```

它回答：

> 这次执行到底发生了什么？

而：

```text
ContextSelection
```

回答：

> 模型当时实际看到了什么？

再结合：

```text
CostProfile
```

回答：

> 为这次结果到底付出了多少资源？

如果这三个对象能稳定下来，DPMS、PPE、KIS、Binggo 之间就能建立真正可复用的数据接口，同时仍保留各自的权威边界。ClipVault 则继续负责可信的本地上下文来源，而不是被强行改造成 Agent Runtime。
