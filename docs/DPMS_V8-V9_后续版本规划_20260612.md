# DPMS_V8-V9_后续版本规划_v1.0_20260612

## 文档定位

本次（2026-06-12）已完成 V5.5（Experiment Runtime）、V6（Risk Intelligence）、V6.5（Learning Runtime）、V7（Governance Runtime）四个里程碑的纯逻辑模块、单元测试与只读 API（详见 [[DPMS_V5.5-V7_RuntimeExpansion_实施记录_20260612]]）。

本文档把 `docs/DPMS_能力演化路线图_v4-v9_20260605.md` 第 11-12 节中较为概括的 **V8 Transition Runtime（策略迁移图）** 与 **V9 Semantic Runtime（语义执行链）**，结合 V5.5-V7 已落地的真实模块/表结构，展开为可直接执行的实施方案 —— 风格对齐 `docs/DPMS_总设计方案_v1_20260611.md` 中 S3-S6 各阶段的「目标 / 建议目录 / 数据结构 / API 设计 / 安全边界 / 验收标准」格式，供下一轮开发直接使用。

**前置事实**（V8/V9 设计的基础）：

- V7 已有 `policy_versions`（`policy_key, version, definition JSON, note, active, created_at`）与 `policy_decisions`（`decision_id, policy_key, policy_version, subject_type, subject_id, inputs, outcome, reasons, created_at`）两张表，以及 `core/app/governance/policy.py` 中的 `validate_policy()` / `evaluate_policy()` / `diff_policies()` / `replay_decision()`。
- `GET /api/governance/policies` 目前在 `policy_versions` 为空时回退到代码内 `DEFAULT_REAL_RUN_POLICY`（version 1）；**尚无写接口**发布新策略版本 —— 这正是 V8 要补的「制度变更」入口。
- V5.5 的 `experiments`/`experiment_branches` 与 V6.5 的 `feature_store`/`model` 已经可以产出「实验结果」「特征解释」，可作为 V8 迁移记录的 `experiment_result` 与 V9 语义链的 `intent`/`policy` 输入来源。

## S7 / V8：Transition Runtime（策略迁移图 / 制度血统）

预计周期（路线图原估）：3-6 个月；按本仓库节奏可拆为 1-2 个迭代落地最小闭环。

### 目标

把“策略/制度如何演化”本身变成可记录、可审计、可回滚的数据，而不是只能在 git log 里翻提交记录：

```text
Policy(real_run_gate) v1 --[reason, trigger, experiment_result]--> v2 --> v3
```

每一次 `policy_versions` 的新增/激活，都必须同时写入一条**迁移记录**，包含：旧版本、新版本、迁移原因、触发事件、相关实验结果、回滚条件、影响范围。**迁移记录是只读追加的审计轨迹**，不替代 V7 的 `evaluate_policy`/`replay_decision`，二者配合：Governance 回答“这一次决策为什么是这个结果”，Transition 回答“规则本身为什么/如何变成现在这样”。

### 建议目录

```text
core/app/transition/
  __init__.py
  engine.py        # 纯逻辑：迁移校验、影响面计算、回滚计划
core/app/api/transitions.py   # 数据访问层 + 治理写接口扩展
core/tests/test_transition_engine.py
frontend/src/pages/TransitionGraph.jsx
```

### 数据结构（`core/app/transition/engine.py`，无 DB 依赖）

- `TRANSITION_REASON_CODES`：固定集合，例如 `("experiment_result", "risk_tightening", "manual_review", "incident_response", "scheduled_review")`。
- `classify_transition(diff: dict) -> "tightening" | "loosening" | "neutral"`：基于 `diff_policies()` 的输出（`added_gates`/`removed_gates`/`changed_required`）判断本次变更是让门禁更严格、更宽松还是中性。**判定规则只做分类，不做拦截**——拦截逻辑在 `validate_transition`。
- `validate_transition(*, from_policy, to_policy, reason_code, rollback_condition, loosening_justification=None) -> (valid, errors)`：
  - `to_policy.version` 必须等于 `from_policy.version + 1`（版本号连续，禁止跳跃/回填）。
  - `reason_code` 必须在 `TRANSITION_REASON_CODES` 内。
  - `rollback_condition` 必填（非空字符串）—— 任何迁移都必须先写明“什么情况下回滚”。
  - 若 `classify_transition(diff) == "loosening"`（例如把某个必需 gate 改为非必需，或移除一个 gate），则 `loosening_justification` 必填，且 `reason_code` 不能是 `"scheduled_review"`（宽松化不能是“常规审查”这种弱理由）。这是 V8 唯一新增的**强约束**：放宽门禁永远需要显式书面理由，体现“安全边界只能更严不能悄悄变松”。
  - `tightening`/`neutral` 变更无额外限制（鼓励随时收紧）。
- `impact_scope(policy_key, diff) -> dict`：基于 `policy_key`（目前只有 `real_run_gate`）与受影响的 gate code，返回受影响的主体类型（如 `subject_type="lottery"`）与一句话描述，供前端展示“这次变更会影响什么”。
- `rollback_plan(transition_record) -> dict`：返回 `{"target_version": from_version, "reason": "rollback", "rollback_condition": ...}`，即“反向迁移”的草稿——本身仍需经过 `validate_transition` 才能真正执行，不会自动生效。

### API 设计

扩展 `core/app/api/governance.py`（或新增 `transitions.py`，二者共用 `policy_versions`/`policy_decisions`）：

- `POST /api/governance/policies`（新增，**admin only + 二次确认**）：请求体 `{policy_key, definition, reason_code, rollback_condition, loosening_justification?}`。
  1. 取当前 active 版本作 `from_policy`；`to_policy = definition`（必须先通过 `validate_policy()`）。
  2. `diff = diff_policies(from_policy, to_policy)`；`validate_transition(...)`。
  3. 校验通过后：在 `policy_versions` 插入新行（默认 `active=0`，即“已发布但未激活”——发布与激活分离，避免“写入即生效”）；在新表 `policy_transitions` 插入迁移记录；写 `audit_event` + `record_event`。
  4. 返回新版本号与 `diff`/`impact_scope`，但**不**改变线上行为（仍按旧 active 版本评估）。
- `POST /api/governance/policies/{version}/activate`（**admin only + 二次确认**）：把指定版本设为 `active=1`，旧 active 版本置 `0`；要求该版本已存在对应 `policy_transitions` 记录（即必须先 `POST /policies` 走过校验），否则 409。激活动作本身也追加一条 `policy_transitions` 行（`reason_code="manual_review"` 或沿用发布时的 reason，`from_version=当前active`, `to_version=目标版本`）。
- `GET /api/transitions?policy_key=real_run_gate`：按 `policy_key` 返回迁移记录列表（`from_version, to_version, reason_code, classification, diff, impact_scope, rollback_condition, requires_extra_review, created_by, created_at`），按时间正序——前端据此画出 `v1 -> v2 -> v3` 的链。
- `GET /api/transitions/{policy_key}/lineage`：返回“当前 active 版本是怎么从 v1 走过来的”完整链路（每一跳的 diff 摘要），用于 V9 语义链的 `transition` 节点。

新增表 `policy_transitions`：

```sql
CREATE TABLE IF NOT EXISTS policy_transitions (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  policy_key VARCHAR(64) NOT NULL,
  from_version INT NOT NULL,
  to_version INT NOT NULL,
  reason_code VARCHAR(32) NOT NULL,
  classification VARCHAR(16) NOT NULL,   -- tightening | loosening | neutral
  trigger_event VARCHAR(128) NULL,
  experiment_id CHAR(36) NULL,
  diff JSON NOT NULL,
  impact_scope JSON NULL,
  rollback_condition TEXT NOT NULL,
  loosening_justification TEXT NULL,
  requires_extra_review TINYINT NOT NULL DEFAULT 0,
  activated_at TIMESTAMP NULL,
  created_by VARCHAR(128) NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_policy_transition_key (policy_key, to_version)
) ENGINE=InnoDB
```

### 安全边界

- **发布 ≠ 激活**：`POST /policies` 只落盘草案 + 迁移记录，绝不改变线上 `evaluate_policy()` 的结果；只有显式 `activate` 才切换 active 版本，且 activate 同样要求 admin + 二次确认。
- **宽松化必须留痕**：`classify_transition` 把“移除/弱化 gate”单独分类，`validate_transition` 强制要求 `loosening_justification`；任何宽松化迁移在 `policy_transitions` 中 `requires_extra_review=1`，前端用醒目样式标出，供管理员复核。
- **版本连续、可回放**：`to_version = from_version + 1` 防止跳版/伪造历史；每个版本仍可通过 V7 的 `replay_decision()` 用历史输入重放，迁移本身不影响既往决策的可回放性。
- 与 V5.5/V6/V6.5 完全相同的总原则：迁移记录与 Transition Graph 是**审计与建议层**，从不直接触发 real-run、断路器或账号操作。

### 测试计划（`core/tests/test_transition_engine.py`，无 DB）

- `classify_transition`：新增 gate（neutral 或 tightening，取决于 `required`）、移除 gate（loosening）、`required: True->False`（loosening）、`required: False->True`（tightening）。
- `validate_transition`：版本号必须连续；`reason_code` 非法被拒绝；`rollback_condition` 缺失被拒绝；loosening 缺 `loosening_justification` 被拒绝；loosening + `scheduled_review` 被拒绝；tightening 不要求 `loosening_justification`。
- `impact_scope`：已知 `policy_key="real_run_gate"` 返回 `subject_type="lottery"`；未知 `policy_key` 返回空影响面而非报错。
- `rollback_plan`：目标版本回退到 `from_version`，且回退草案本身仍需 `validate_transition` 才视为合法。

### 验收标准

- 能在不影响线上行为的前提下提案一个新策略版本，看到结构化 diff 与影响面；激活后旧决策仍可用旧版本重放，新决策使用新版本。
- 任意一次“宽松化”提案，若未填写理由会被拒绝；填写后会被标记为需复核，并在 Transition Graph 上与“收紧”类变更视觉区分。
- `GET /api/transitions/real_run_gate/lineage` 能完整还原从 v1 到当前 active 版本的每一跳。

### 前端：`frontend/src/pages/TransitionGraph.jsx`

- 时间线/链路视图：每个版本一个节点，标注 `version`、`reason_code`、`classification`（颜色区分 tightening=绿/loosening=红/neutral=灰）、`created_at`；当前 active 版本高亮。
- 点击节点展开 diff（新增/移除的 gate、`required` 变化）与 `impact_scope`。
- Admin 表单：粘贴/编辑新策略 JSON → 预览 diff/classification → 若 loosening 则要求填写 `loosening_justification` → 提交（`POST /policies`，二次确认）→ 单独的“激活”按钮（`POST /policies/{version}/activate`，二次确认）。
- 安全提示文案：“发布不等于生效；宽松化变更需要书面理由并将被标记复核”。

## S8 / V9：Semantic Runtime（语义执行链）

预计周期（路线图原估）：6-12 个月；本仓库范围内先落地“只读语义追踪”最小闭环。

### 目标

把 `Intent -> Institution -> Policy -> Transition -> Execution` 五层在**一次查询内串起来**，让任意一次执行（或一次被拦截的尝试）都能回答：

- **Intent**（意图）：这次为什么会被考虑？—— 来自 V5 策略评分 `/lotteries/{id}/strategy/explain` 与 V6.5 `/learning/predictions` 的解释。
- **Institution**（制度）：当时适用的是哪个策略对象？—— `policy_key` + 当时 active 的 `version`。
- **Policy**（策略决策）：门禁评估结果是什么？—— V7 `policy_decisions` 中该 subject 的最新一条记录（`outcome`/`reasons`/`next_action`）。
- **Transition**（迁移）：这个策略版本是怎么演化来的？—— V8 `policy_transitions` 的 lineage。
- **Execution**（执行）：实际发生了什么？—— `task_runs`/`lotteries` 的状态与结果。

V9 的重点**不是新增决策能力**，而是新增一个**纯聚合的解释/审计视图**：把已经存在于 V5/V6.5/V7/V8 各表中的数据按同一个 subject 串成一条链。

### 建议目录

```text
core/app/semantic/
  __init__.py
  trace.py          # 纯逻辑：把五段输入拼装成统一的 SemanticTrace 结构
core/app/api/semantic.py
core/tests/test_semantic_trace.py
frontend/src/pages/SemanticTrace.jsx
```

### 数据结构（`core/app/semantic/trace.py`，无 DB 依赖）

- `build_semantic_trace(*, intent, institution, policy_decision, transition_lineage, execution) -> dict`：纯函数，输入均为已经从各 API/表中取出的 plain dict/list，输出统一结构：

```json
{
  "subject_type": "lottery",
  "subject_id": "123",
  "intent": { "mode": "...", "score": {...}, "top_drivers": [...] },
  "institution": { "policy_key": "real_run_gate", "active_version": 3 },
  "policy": { "decision_id": "...", "outcome": "block", "reasons": [...], "next_action": "..." },
  "transition": { "lineage": [ {"version": 1, ...}, {"version": 2, ...}, {"version": 3, ...} ] },
  "execution": { "status": "pending", "task_runs": [...] },
  "narrative": ["...逐条人类可读说明..."]
}
```

- `narrative_lines(trace) -> list[str]`：把上述结构转成一组简短陈述句（中/英各一套模板），例如：“该目标因 `value_score=82` 与 `top_driver=win_rate` 被策略引擎评为 S 档；当前生效的 `real_run_gate` 是 v3（v1 因 `experiment_result` 收紧了 `recent_shadow_run`）；v3 评估结果为 `block`，原因是 `recent_shadow_run` 未满足；因此执行状态停留在 `pending`。” —— 这是 V9 “自我解释”的核心产出，且**完全由已记录的数据派生**，不引入新的判断逻辑。
- `consistency_checks(trace) -> list[str]`：轻量一致性检查（仅用于提示，不阻断），例如policy outcome 为 `block` 但 execution 状态却是 `succeeded`（数据不一致告警）、`institution.active_version` 与 `policy.policy_version` 不一致（说明决策发生在策略变更之前，提示“以历史版本回放”）。

### API 设计

新增 `core/app/api/semantic.py`（前缀 `/api/semantic`，**只读**）：

- `GET /trace/{subject_type}/{subject_id}`（当前仅支持 `subject_type="lottery"`）：
  1. `intent`：调用既有 `explain_lottery_strategy(lottery_id)`（V5/S2，复用 `compute_strategy_item(..., include_breakdown=True)`）与可选的 `/learning/predictions` 条目。
  2. `institution`：`GET /api/governance/policy` 的 `policy_key`/`version`。
  3. `policy`：`policy_decisions` 中按 `subject_id` 取最新一条（即 `GET /api/governance/decisions?subject_id=...&limit=1`）。
  4. `transition`：`GET /api/transitions/{policy_key}/lineage`（V8）。
  5. `execution`：该 lottery 的 `task_runs`（状态、模式、时间）。
  6. 调用 `build_semantic_trace()` 拼装，附加 `narrative_lines()` 与 `consistency_checks()`。
- 全程零写操作；任一来源缺失时该字段为 `null`/空列表，`narrative_lines` 对缺失部分输出“暂无记录”而不是报错（fail-soft 用于展示，但**不**影响 V7/V8 的 fail-closed 门禁本身）。

### 安全边界

- 纯聚合 + 叙述生成，**不产生任何新的权限或决策**；`narrative`/`consistency_checks` 仅用于展示，绝不作为 `evaluate_policy`/real-run 门禁的输入（避免“解释文本反向影响决策”的循环依赖）。
- 与 V5.5-V8 一致：只读、advisory、可解释、可回放——V9 是把这四个性质**可视化**，而不是新增第五个性质。

### 测试计划（`core/tests/test_semantic_trace.py`，无 DB）

- `build_semantic_trace`：各输入齐全时输出结构完整；任一输入为 `None`/空时对应字段为空而不抛异常。
- `narrative_lines`：针对“allow + succeeded”“block + pending”“策略版本变更后”等典型组合，断言关键信息（outcome、next_action、active_version）出现在生成的句子中；中英文模板均覆盖。
- `consistency_checks`：构造“block 但 execution=succeeded”“decision 版本 < active 版本”两类不一致样例，断言能给出对应提示；一致样例返回空列表。

### 验收标准

- 任选一个有过 real-run 门禁评估记录的 lottery，`GET /api/semantic/trace/lottery/{id}` 能在一次请求内返回 intent/institution/policy/transition/execution 五段数据与至少 3 条 `narrative`。
- 当该 lottery 关联的策略版本发生过 V8 迁移时，`transition.lineage` 能体现版本演化；`narrative` 中能提到“当前版本相对历史版本的关键变化”。

### 前端：`frontend/src/pages/SemanticTrace.jsx`

- 输入 `lottery_id` → 展示五段卡片（Intent / Institution / Policy / Transition / Execution）+ 一段自然语言叙述（`narrative`）；`consistency_checks` 若非空则以提示横条展示。
- 可作为 Governance 页“评估真实运行门禁”面板的“查看完整语义链”跳转目标，避免与 V7 页面重复造轮子。

## 工程节奏建议

1. **V8 优先且收益明确**：直接补全 V7 留下的“策略变更无审计轨迹”缺口，且复用现有 `policy_versions`/`diff_policies`，改动面集中在 `core/app/transition/` + `governance.py` 扩展 + 一个新表，风险可控。
2. **V9 依赖 V8**：`transition.lineage` 是语义链五段中的一段；建议 V8 先落地并跑通 `policy_transitions` 数据后再实现 V9，否则 `transition` 段长期为空，`narrative` 缺一角。
3. 两者均遵循既定模式：纯逻辑模块（`engine.py`/`trace.py`，无 DB）→ 单元测试 → 薄 API 层 → `ensure_*_schema()` 幂等迁移 → 前端页面 → `docs/` 实施记录 + Obsidian 时间线 + Git 提交。
4. 安全边界回归测试建议清单（V8/V9 落地后追加到既有 164 项之上）：
   - fail-closed / advisory-only / 可回放 三项性质在新增模块中各自至少 1 个直接测试。
   - “宽松化必须留痕”（V8）与“语义层不反向影响决策”（V9）各至少 1 个直接测试，作为本阶段新增的安全不变量。

## 风险与注意事项

- `policy_versions`/`policy_decisions` 当前为空表（V7 刚落地），V8 的 `POST /policies` 在首次使用前需要先有一条“v1 = `DEFAULT_REAL_RUN_POLICY`”的种子记录，否则 `from_policy`（当前 active 版本）取不到值——建议在 `ensure_governance_schema()` 中补一次性 seed（`INSERT IGNORE`，`version=1, active=1, definition=DEFAULT_REAL_RUN_POLICY`），这样第一次迁移的 `from_version` 就是 1，而不是特例处理“无历史版本”。
- V9 的 `GET /api/semantic/trace` 聚合了 4-5 个数据源，注意控制单次查询的延迟（必要时分批/缓存），但**不**引入写缓存到决策路径——语义层永远是只读旁路。
