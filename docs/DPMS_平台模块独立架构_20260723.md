# DPMS 平台模块独立架构

## 目标

DPMS 的 Bilibili、Weibo、Xiaohongshu、Douyin 是四个相互独立的业务模块。
一个平台的发现源、目标格式、规则策略、账号凭据、执行路径或动作集合发生变化时，
不得改变其他平台的校验、计划哈希、调度选择或用户界面。

平台模块共享的仅是基础设施能力：数据库事务、账号租约、Outbox、事件审计、
熔断器、证据存储、加密原语和任务消息信封。公共基础设施不得推断平台业务语义。

## 平台模块职责

每个平台模块独立声明并实现：

- 支持的发现源类型及其校验、扫描实现；
- 目标 URL 校验、短链解析和 canonical identity；
- Action Plan/执行策略的版本、动作集合、顺序和 payload；
- 支持的 dry、shadow、real 执行模式；
- 账号凭据类型、校准要求和账号适用规则；
- 执行适配器、能力门禁和平台专属证据；
- 前端导入器、表单能力和错误提示。

“可接受目标类型”和“可自动执行目标类型”是两个独立契约。例如 Bilibili 的
视频与专栏可以作为发现/管理目标，但当前 API real-run 只支持动态/opus；三端
描述符必须分别声明并校验这两个集合，不能因 URL 可导入就暗示它可自动执行。

## 共享接口原则

平台注册表只负责按 `platform_id` 定位模块，不维护跨平台业务默认值。
共享消息只携带平台、契约版本、不可变 payload 及其 hash；payload 由目标平台模块解释。
不允许由公共代码自动将一个执行路径降级或切换为另一个路径。

```text
Platform Registry
  ├─ bilibili       discovery + target + strategy + execution
  ├─ weibo          discovery + target + strategy + execution
  ├─ xiaohongshu    discovery + target + strategy + execution
  └─ douyin         discovery + target + strategy + execution

Shared Kernel
  ├─ database / transactions
  ├─ leases / circuit breakers
  ├─ outbox / event audit
  ├─ evidence storage
  └─ task envelope / cryptography
```

## 隔离验收条件

1. 非 Bilibili 平台创建 `keyword` 或 `up` 发现源时必须立即拒绝，不能保存为静默空跑的 active 来源。
2. 各平台 Action Plan 校验只读取本平台契约；给 Douyin 新增动作不得改变其他平台的 plan hash。
3. 微博 OAuth 与浏览器会话是微博模块内部的两个显式执行路径，不允许 UI 或 Core 隐式混用账号。
4. 手动 Shadow Run 入队前必须验证本平台所需观察选择器，缺失时返回可操作的 blocker。
5. 平台模块必须有独立单元测试；共享层只测试接口一致性和平台隔离，不复制平台业务规则。
6. 在隔离测试中替换一个平台的发现、Action Plan 或 Shadow 契约时，其他平台的
   动作顺序、计划哈希、选择器判定和执行路由保持不变。

三端描述符还必须通过契约一致性检查，避免 Core、Worker 与前端分别演进后出现
动作顺序、发现源、执行路径、凭据类型或目标类型漂移：

```powershell
python scripts/platform_contract_parity.py --strict-target-kinds
```

## 当前运行时边界

- 四个平台在 Core、Worker 和前端分别拥有独立的业务描述符与策略入口，但仍在
  同一组服务进程中运行，共享数据库、Redis、租约、Outbox 和证据存储。
- 每个平台有一个标准通道 `lottery_tasks:<platform>` / `workers:<platform>`，以及一个
  版本化 Repair-only 通道 `lottery_repair_tasks:v1:<platform>` /
  `repair-workers:v1:<platform>`。八个 stream 各自拥有独立读取循环、Pending Entry
  List、recovery 循环和 32 条有界在途预算，因此任意单 lane backlog 不占用其他 lane
  的读取容量。标准信封明确拒绝 `execution_intent_kind=repair`；Repair 通道只接受
  `mode=real_run` 且 kind 为 `repair` 的信封。旧 Worker 不认识新 stream/group，
  新 Worker 也不会在标准 lane 执行 Repair。两个同平台 lane 在每个 Worker 进程内
  共享同一执行锁，跨平台任务可并行，且只在权威 claim/settlement 完成后确认；多
  Worker 部署仍可并行处理同平台的不同权威任务，不应把该锁误解为集群级串行保证。
- Outbox 不再按全局 ID 单队列串行 relay。四个平台的标准与 Repair stream 各自拥有
  精确按 `stream_key` 查询的 relay/reclaim 循环；历史 stream 在排空开关启用时使用独立兼容 lane，
  adapter probe 等非任务事件进入排除所有任务 stream 的共享 lane。某个平台前缀
  backlog、失败重试或慢 `XADD` 不会占用另一个平台的 Outbox 扫描窗口。
- 队列指标按平台、标准/Repair lane 分别读取 pending、lag 和 consumer。任一 lane
  的 Redis 观测失败时，该 lane 与相应平台聚合返回 `null` 并标记
  `*_available=false`，不会把读取失败折算成零；legacy 排空判定还必须同时看到
  Redis pending/lag 与数据库未投递 Outbox 均可观测且为零。
- 平台 transport readiness 不使用全局 Worker 数兜底。每条标准/Repair lane 的
  Redis consumer 身份必须与 45 秒内同名 DB heartbeat 相交，避免死亡 consumer
  因仍持有 PEL 而被误报在线。Worker 的 task/probe/calibration consumer 与
  heartbeat 共享同一条有界 `hostname:pid:nonce` 身份；同主机多进程和 PID
  复用后的新进程都不会合并成一个 Redis consumer，也不能借用兄弟/旧进程的
  heartbeat。`outbox_events.pending/sending` 按平台各执行一个
  `(stream_key,status,id)` 索引查询；每次状态进展后允许 120 秒 relay 窗口，超过窗口仍未投递
  才标记该平台 `*_task_outbox_stalled`。单平台 Outbox 查询失败只使该平台
  `outbox_available=false`，兄弟平台保持可判定。每条 lane 的 Redis 指标、各平台
  Outbox、heartbeat 及平台 readiness 数据读取都使用 5 秒 deadline；driver/network
  永久挂起会被转成 fail-closed unavailable，而不会拖住整个 endpoint。
- Repair dispatch 的 lane-health contract v2 保留最后一次成功 `XREADGROUP` 的年龄，
  并独立记录固定枚举的循环进展操作、单调时钟年龄、0–32 in-flight 计数和固定上限；
  不记录 task ID、消息 ID、payload 或异常文本。通常只接受 45 秒内的精确 lane 读取。
  若读取年龄已超过 45 秒，只有该 lane 曾成功读取、当前恰好占满 32 个有界 in-flight、
  `capacity_wait` 每 10 秒仍推进且连续 Redis 失败为 0 时，才视为健康。未满、进展过期、
  Redis 失败、未知 contract、Worker 监督退出，以及 Redis consumer 与 DB heartbeat
  身份不相交都继续 fail-closed。Core 保留 v1 近期读取证据解析仅用于停机升级后的
  历史观测，不会把 v1 证据当成新旧 Worker 混跑许可，也不会把陈旧读取解释成满载存活。
- `/api/metrics/overview` 保留 `workers_online`、legacy 指标和已有队列字段，并新增
  `workers_online_by_platform`、`task_transport_by_platform`、
  `task_outbox_undelivered_by_platform` 与 `task_outbox_stale_by_platform`。
  `/api/metrics/readiness` 的 `ready_for_dry_run/shadow_run/real_run` 还要求目标平台
  标准 transport ready，Repair lane 状态由 `repair_transport_ready` 单独暴露，
  `ready_for_repair_dispatch` 还要求账号/adapter/global real-run capability ready；
  生产检查要求四个平台标准/Repair transport 分别 ready。
- 队列拓扑只在 `shared/task_streams.py` 定义一次；Core/Worker 的
  `app/task_streams.py` 是保持既有 import 路径的薄 re-export，并通过对象 identity
  测试阻止两端再次复制、漂移。容器镜像会复制 `shared/`，本地直接运行测试时必须把
  仓库根目录和对应服务目录同时放入 `PYTHONPATH`；修改共享包后需重建两端镜像。
- Compose Redis 使用命名卷 `redis-data:/data` 并启用 AOF
  `appendonly yes / appendfsync everysec`。此外，每条任务 lane 都有独立的
  continuity token/state；Outbox 的每条成功投递记录保存由 XADD 时 Redis
  `run_id`、全局 token、精确 stream key 与 lane token 组成的 epoch。token
  通过原子 SET-NX + GET Lua 创建，因此多个 Core 首次启动或数据集丢失后会收敛到同
  一个值。Core 启动时及后台循环用
  `runtime_settings.redis_task_stream_epoch` 的 `FOR UPDATE` 行锁协调多个 Core
  实例。epoch 变化只回拨 `outbox_events.status=sent`、对应
  `task_runs.status=queued`、属于八条平台标准/Repair 或 legacy 精确任务 stream 且投递 epoch
  不同的行。`running`/终态任务、非任务 stream、未知 future stream 均不重放。
  XADD 前后 epoch 不一致或二次确认不可用时，当前回执会条件回拨，避免 Redis 重启
  恰好落在 XADD 与 DB sent 回执之间形成新孤儿窗口。
- 周期性 epoch 修复查询从
  `task_runs.idx_task_run_status(status,created_at)` 的 `queued` 小集合驱动，再用
  `outbox_events.uk_outbox_dedup(dedup_key)` 单行点查；不会从历史 `sent` Outbox
  扫描，因为终态任务的旧 epoch 永远不会被回拨，按该方向扫描会让维护成本随历史
  数据持续增长。生产 schema verifier 和 0016 迁移同时校验/修复这两个索引。
- 首次部署 `0016_outbox_redis_delivery_epoch.sql` 后，旧 sent+queued 任务的 epoch
  为 NULL，会被保守重放一次；重复消息仍由 DB task claim/lease 拦截。Redis ACL
  至少要允许协议使用的 `INFO`、`EVAL`、`GET`、`SET`、`DEL`、`INCR`、`EXPIRE`、
  `XLEN`、`XADD`、`XACK`、`XDEL`、`XRANGE`、`XREADGROUP`、`XCLAIM`、`XPENDING`、
  `XINFO GROUPS`、`XINFO CONSUMERS`、`SADD`、`SISMEMBER`、
  `SMEMBERS`、`SREM`、`SCARD` 以及对应的精确 key pattern，并显式禁止
  `FLUSHDB`/`FLUSHALL`、`XGROUP DESTROY`、删除 task stream 或覆写 continuity key。
  通知/pubsub 等非队列功能应由独立角色按需授权。任一启动期 continuity 能力不可用时
  Core 在开始接受请求前 fail-closed。终态清理阶段的 ACL 错误会安全保留 stream entry，并由 lane
  `XLEN` 暴露为 retention backlog。多实例共享行锁
  只协调回拨，不串行化四个平台各自的 relay。所有 Core 实例必须连接同一个逻辑
  Redis primary；若错误地连接不同后端，彼此不同的 run_id/token 会造成保守重放
  抖动。全局 token 能检测同一进程内的 `FLUSHDB` 或 continuity key 删除；每条
  lane 在曾被观测为非空，或 relay 在 `XADD` 前已将其武装为 nonempty 后，若
  `XLEN` 变为 0，则只轮换该 lane token 一次。协调器因此只重放该精确 lane 的
  sent+queued 行，不影响兄弟平台，也不混用标准与 Repair 通道。这个保证只覆盖
  “整条 lane 变空”：选择性 `XDEL` 后仍有其他条目时不会触发；有权限者删除后精确
  恢复旧 token/state 也可规避检测。业务 Redis 身份仍必须由 ACL 禁止
  `FLUSHDB`/`FLUSHALL`，并禁止删除任务 stream/consumer group 或覆写所有
  continuity token/state；上述边界必须由最小权限与运维审计覆盖。
- Core/Worker 的 Redis 连接池默认值和配置下限均为
  `REDIS_MAX_CONNECTIONS=64`。Worker 常驻连接预算约为
  `8 task readers + 4 probe readers + 4 calibration readers +
  2 control legacy fan-out + 1 login + 1 pubsub = 20`；30 秒 pending
  refresh、60 秒 recovery、ACK、Outbox 与执行期读写还需要突发余量。小于 64
  会在配置加载阶段 fail-fast，避免连接池耗尽被误报成随机平台 lane flap。已有部署
  若显式设置了 32，必须先把环境配置提升到至少 64，再执行停机切换。
- Worker 角色拆分后，BrowserPool 的 `init()` 只校验容量，不启动 Playwright；
  `get_available_browser`、账号 persistent context 或 transient login context 的首次
  真实调用才初始化对应进程的浏览器运行时。control 与四个平台 Worker 在没有浏览器
  工作时因此保持零 Chromium，不会在部署启动瞬间把原先的 N 个浏览器隐式放大成
  5N。`WORKER_MAX_BROWSERS` 和 `WORKER_MAX_PERSISTENT_CONTEXTS` 仍分别是每个进程的
  上限；若五个角色同时存在浏览器工作，部署总预算必须按各服务配置之和计算，不能把
  一个环境变量值误当成全局 semaphore。
- 历史 `lottery_tasks/workers` 是只允许标准任务的兼容排空入口，不会直接进入 Worker：
  Core fan-out consumer 先用不可变 Outbox payload、任务行和 stream/platform 绑定
  验证权威性，再通过单个 Redis Lua 操作完成幂等标记、向目标平台 stream `XADD`
  和旧消费组 `XACK`。进程在任意边界退出都不会留下“已 ACK 但未转投”的窗口，重试
  也不会重复转投；未知平台、缺失字段、payload 不一致或缺少 Outbox 权威的条目保留
  在旧 PEL，不能被误判为排空。历史 stale PEL 也复用同一 fan-out 路径，因此旧队列
  的任意单平台消息前缀不占用任何平台 Worker 的在途预算。带
  `execution_intent_kind=repair` 的 legacy 消息会保留并 fail-closed，绝不 fan-out
  到标准通道。
- 唯一的缺失平台兼容例外是早期 Bilibili 信封：Outbox 与 legacy 消息必须同时缺少
  `platform`，并且锁定的 lottery、account 两个数据库权威都必须仍为 Bilibili，
  Core 才在内存中回填后转投。该规则不扩展到其他平台，无法双重确认时条目保留在 PEL。
- fan-out provenance marker 使用 Redis Set 记录首次转投及恢复重投形成的
  `stream/task/message` 绑定链，而不是仅记录可能跨 stream 碰撞的 Redis message
  ID。目标消息处理中或重投时 marker 必须保留；只有任务已经权威终态、当前绑定匹配，
  且 Lua 先 `XACK` 当前组后确认该 lane 的所有 consumer group 都已越过精确消息 ID、
  所有 PEL 都不再持有该 ID，Worker/Core 才在同一个 Lua 操作内 `XDEL` 目标消息并
  移除当前 marker binding；只有 Set 已无其他恢复重投 binding 时才删除 marker key。
  普通平台 lane 的终态消息也使用同一“全组确认后删除”规则；
  legacy stream 继续保留作迁移 provenance，数据库 Outbox 历史不做物理删除。
  `/api/metrics/overview.task_streams[*].length` 暴露各 lane `XLEN`，
  `task_stream_length` 与 `task_stream_length_by_platform` 提供 fail-closed 聚合。
  stale recovery 原子写入新 fan-out binding 并 ACK 旧消息后，也只在全组确认时
  删除被替代的旧目标消息和旧 binding，新的恢复 provenance 保持有效。
  这样既避免 ACK 与清理之间的崩溃窗口，也避免正常完成的 marker 无界累积。历史
  版本可能留下的 marker 只在确认对应任务终态和所有目标 PEL 已收敛后，才可纳入
  受控物理清理。
- `LEGACY_TASK_STREAM_DRAIN_ENABLED=false` 只停止 Core 的旧入口 fan-out 与 stale
  recovery，不删除 stream，也不影响新的四个平台 lane。
- Redis 入口使用一次性随机 bootstrap identity，按共享固定 topology 在运行身份可用前
  幂等执行 `XGROUP CREATE ... 0 MKSTREAM` 并逐组验证；随后通过 `ACL LOAD` 禁用
  bootstrap。Worker/Core 首次读取和 `NOGROUP` 恢复只执行 `XINFO GROUPS` 校验并
  fail-closed，不再自行创建 group。Redis/PEL 丢失后必须先重跑 bootstrap，不能让
  运行身份把缺失 topology 当作普通竞争条件。
- PEL 不是 `running` 状态的恢复权威。Core 为四个平台分别运行一个数据库扫描器，
  每 30 秒最多读取 32 条 `task_runs.status=running` 且 worker lease 已过期的候选；
  `0017_stale_running_recovery_index.sql` 会新增 recovery 专用的 lottery
  `(platform, status, id)` 索引（不改写既有 `idx_pending`），让候选读取先限定到目标业务平台，再通过
  task 的 `(lottery_id, status, lease_expires_at, task_id)` 定位该 lottery 的过期
  owner；另用 `(status, lease_expires_at, task_id)` 支撑全局 backlog 指标，避免从
  终态历史方向扫描。
  多 Core 实例通过 Outbox→task→lottery→account 的行锁顺序和条件状态更新收敛，
  不依赖 Redis dedup key。`dry_run`/`shadow_run` 只有在不可变 Outbox payload、
  平台、lottery execution lock、ready account 及同一最新账号操作 lease generation
  全部仍精确匹配时，才原子恢复 task=queued、lottery=claimed、Outbox=pending；
  账号 lease 已过期或被新 generation 替代时不会复活旧 fence，而是把无外部副作用
  的任务安全终止并释放 lottery。`real_run`（含 Repair）无论 intent 当前文字状态如何
  都不会自动重投：任务转为 failed+`reconciliation_required`，started intent 转为
  structured unknown，账号进入 cooling，平台 breaker 打开，lottery execution lock
  与账号操作 lease provenance 保留给人工对账。指标
  `/api/metrics/overview.stale_running` 和 readiness summary 的
  `stale_running_tasks` 按平台、模式统计剩余 DB backlog；数据库观测失败时返回
  `available=false`，不能把不可观测误报为零。
- Account Calibration、Adapter Probe 的实时消费与 stale recovery 分开运行；历史校准
  消息会在派发任务内以数据库权威平台回填到对应 lane，恢复重放也复用同一平台锁。
  Probe 的完整 claim/执行/结算生命周期受 240 秒截止时间约束，早于五分钟 stale
  判定；终态事件与租约释放通过共享事务 Outbox 持久化，证据物化失败时保留 PEL
  供独立恢复支线幂等补偿。
- 默认部署将故障域拆成一个 `core-api` 控制进程、四个精确平台 Core runner、一个
  名为 `worker` 的控制 Worker，以及四个精确平台 Worker。`core-api` 只拥有共享
  recovery、通知、Outbox 与全局 scheduler；每个 Core runner 只预检并加载自己的
  平台模块，只拥有该平台的 discovery、recovery、Outbox 与 scheduler。控制 Worker
  只拥有登录、task-outbox、heartbeat retention，并在兼容排空开关启用时拥有
  Probe/Calibration 的 legacy fan-out；每个精确平台 Worker 只预检并加载自己的平台执行模块，只消费该平台的
  task、Probe 与 Calibration lane。`all` 角色仅作为代码级兼容模式，默认 Compose
  不与上述拆分拓扑同时运行，避免重复消费和重复 fan-out。
- 单个平台模块导入失败会让该平台 runner/Worker 启动失败，但不会阻止兄弟平台和
  `core-api` 启动。`core-api` 的共享关键后台任务异常、被取消或意外返回后，
  `/api/health` 与除健康检查外的全部 API 都返回 503；平台 runner 与 Worker 使用
  `FIRST_COMPLETED` 监督各自关键循环，任一循环提前结束都会取消本进程兄弟循环并
  退出，由编排器依据既有 restart policy 重启。
  `/api/health` 在数据库或 Redis 不可用时也返回 503，而不是仅在响应体中标记
  `degraded` 后仍返回 200。
  `core-api` 仍选择在进程内 fail-closed 而不是主动退出，因此仍需外部健康检查执行
  实例替换；Docker Compose 的 `restart: unless-stopped` 不会仅因 unhealthy 自动重启。

  facade。新增业务规则必须先进入目标平台模块，再由 facade 转发，不能反向成为

  保留并提交原行，由 Core 将该平台短链逐行记录为 invalid，但兄弟平台和同平台直接
  链接继续导入，且不会为超限行发起重定向请求。前后端的每平台短链 host、预算与

  evidence 使用请求 generation、发起账号和响应账号三重校验，切换账号后到达的旧

  通过整页重新加载建立新的浏览器模块图后重试，避免把同一模块图中已缓存的 import
  失败误报为可原地恢复。

## 迁移策略

采用兼容式渐进迁移：先用平台注册表包装现有实现，再分别迁移发现、策略、Worker
执行和前端能力，最后删除中央平台分支。迁移过程中保留现有 API 字段、任务信封和
fail-closed 安全门禁；任何持久化格式变化都需单独设计迁移和兼容期。

队列迁移按以下顺序执行：

1. 启用 Repair 专用通道前暂停 Repair dispatch，并确认标准 lane 与数据库中不存在
   已排队/运行的历史 Repair 任务。旧版本曾把 Repair 写入标准 stream，而 Outbox
   未保存 Redis message ID，不能在线安全撤回；未排空时必须停机式完成旧任务或人工
   对账，不能依赖新协议自动迁移。
2. **停止全部旧应用后一次性切换协议**：当前版本同时改变 Schema、Redis ACL、固定
   consumer-group topology、任务/Repair 信封和控制队列，不支持滚动混跑。应用迁移前
   必须暂停新派发，完成仍在运行的 real-run/Repair 对账，并使用旧部署清单停止全部旧
   Core、全部旧 Worker 和旧 Nginx；不得保留一个旧 Worker 处理所谓升级窗口。
   保留 MySQL/Redis 数据卷、AOF、Stream、PEL 和 Outbox 现场。

   新清单先启动 MySQL 与 Redis；既有 MySQL 卷必须显式、幂等地执行
   `/usr/local/bin/dpms-mysql-provision-roles`，因为镜像 init hook 不会在既有卷上
   重跑。Redis 入口使用一次性随机 bootstrap 身份预建并验证固定 group，随后通过
   `ACL LOAD` 禁用该身份。两项验证成功后，运行独立 `core-migrate`；运行时 Core
   和 Worker 永不执行 DDL。

   migration ledger 和生产 verifier 全部通过后，先启动 `core-api`，再启动
   `core-bilibili-runner`、`core-weibo-runner`、`core-xiaohongshu-runner` 和
   `core-douyin-runner`。确认目标 runner 健康后，启动名为 `worker` 的 control
   Worker 与四个精确平台 Worker，最后启动 Nginx。每个精确平台 Worker 必须依赖
   `core-api` 与同平台 Core runner 健康，不能依赖兄弟平台 runner。推荐顺序为：

   ```powershell
   $composeArgs = @('--env-file', '.env', '--env-file', '.env.mysql-admin', '--env-file', '.env.redis-admin')
   docker compose @composeArgs up -d --build --wait mysql redis
   docker compose @composeArgs exec -T mysql /usr/local/bin/dpms-mysql-provision-roles
   docker compose @composeArgs --profile migration run --rm --build core-migrate
   docker compose @composeArgs up -d --build --wait core-api core-bilibili-runner core-weibo-runner core-xiaohongshu-runner core-douyin-runner
   docker compose @composeArgs up -d --build --wait worker worker-bilibili worker-weibo worker-xiaohongshu worker-douyin
   ```

   新 Core 拆分拓扑同时认识新旧标准 stream 和 Repair v1 stream，并负责把停机前
   留存的 legacy 标准条目转投标准 lane；这是数据兼容，不是进程混跑兼容。旧版本
   已领取但未结算的任务必须在步骤 1 完成或进入人工 reconciliation，不能交给新旧
   Worker 竞速。启动前必须应用
   `0015_task_outbox_stream_lane_index.sql` 和
   `0016_outbox_redis_delivery_epoch.sql`，以及
   `0017_stale_running_recovery_index.sql`；
   Weibo Worker 可以结算 `outcome=rejected` 前还必须先由 Core 应用
   `0018_external_action_rejected_outcome.sql`，会创建或切换 execution intent 的
   Core 版本还必须应用 `0019_execution_intent_current_head.sql`；平台校准恢复需要
   `0020_account_calibration_platform_recovery_indexes.sql`；账号批量 readiness 上线前
   必须应用 `0021_risk_events_account_created_index.sql`；策略查询硬预算需要
   `0022_strategy_query_budget_indexes.sql`；滚动风险状态读取需要
   `0023_account_active_risk_state.sql`；持久化 Profile 清理 intent 需要
   `0024_account_profile_cleanup_intents.sql`；跨 Worker persistent Chromium context
   的数据库 lease 需要 `0025_account_profile_context_leases.sql`，最终删除仍必须
   获得同一 Profile 的跨进程文件锁。`0022` 遇到同名但列序、唯一性、前缀或可见性
   漂移的索引会中止迁移并要求人工处置，不会用不可逆的 `DROP+ADD` 静默覆盖旧定义。
   `0023` 的一次性回填会扫描最近 24 小时风险历史，发布前应在同规模副本测量耗时。
   生产 schema verifier
   会拒绝缺失或列序
   漂移的 `idx_outbox_stream_status_id(stream_key,status,id)`，避免独立 lane 退化为
   对其他平台 pending 前缀的重复全扫描，也会拒绝缺少
   `outbox_events.redis_delivery_epoch` 或
   `idx_risk_account_created_id(account_id,created_at,id)`、滚动风险状态表或精确触发器
   定义的部署。

   回滚必须先停止全部新 Nginx/Core/Worker，再恢复经演练且彼此兼容的旧应用、
   Schema、Redis ACL 与 topology 组合；不得在新进程仍运行时放宽旧 ACL，不得删除
   Stream/PEL/AOF 现场，也不得盲目执行会丢弃多代 intent 或清理 intent 的 down
   migration。无法证明备份兼容时保持停机并人工对账。
3. 保持 Core 的 `LEGACY_TASK_STREAM_DRAIN_ENABLED=true`，让历史 stream 继续
   fan-out、恢复和确认；新派发只进入目标平台的新 stream。
4. 通过 `/api/metrics/overview` 确认 `legacy_pending=0`、
   `legacy_lag=0`、`legacy_outbox_undelivered=0` 且
   `legacy_drain_complete=true`；完成值已经同时绑定 Redis PEL/lag 和数据库
   `outbox_events` 中旧 stream 的 `pending/sending` 行数，任何观测不可用都不能
   视为已排空。变更发布配置前仍建议直接查询 Outbox 做一次独立审计。
5. 在 Core 发布配置中把开关设为 `false`。保留旧 stream 供审计，
   不自动 `XDEL`/删除消费组；需要物理清理旧 stream、消费组或历史遗留 marker
   时另走受控、可回滚的运维流程。

`REPAIR_TASK_PROTOCOL_VERSION` 不是可直接原地递增的升级开关。未来引入 v2 时必须把
v1/v2 作为并存的显式 binding，先让 Core 保持 v1 recovery/Outbox drain，再按指标
确认 v1 的 pending、lag 和未投递 Outbox 全部收敛；直接把常量从 1 改为 2 会让 v1
任务失去自动消费与恢复入口。

### Probe 与 Account Calibration 控制队列

共享基础设施只保留 topology、Outbox、continuity 和指标协议，实时业务请求按平台
隔离：

- Probe：`adapter_probe_requests:<platform>` /
  `adapter-probers:<platform>`；
- Account Calibration：`account_calibration_requests:<platform>` /
  `account-calibrators:<platform>`。

每个平台分别运行 consumer、有限预取、pending refresh、PEL reclaim 和数据库
recovery。校准 lane 的平台取自持久化 `account_calibrations` / `accounts` 绑定，
Redis 信封不能选择凭据、导航目标或执行类型；信封含 credential、Cookie、Token
等字段时直接 fail-closed。Core 与 Worker QR producer 都在账号业务变更的外层事务
内写入 calibration row 和目标平台 Outbox，消除了账号已经进入 `warming`、但
Redis 请求不存在的双写窗口。Outbox 重试耗尽只会失败仍为 `queued` 的精确校准；
若它仍是该账号最新校准且账号仍为 `warming`，才恢复信封中受白名单约束的原安全
状态。已被 Worker claim 为 `running` 或已有更新校准时不会被旧 relay 回执覆盖。

历史 `adapter_probe_requests` 与 `account_calibration_requests` 由独立
`:legacy-fanout` group 从 ID 0 开始读取，因此也覆盖旧 group 已 ACK 或仍在 PEL、
且没有 Outbox 的历史条目。Probe fan-out 会验证完整 Outbox authority；对早期没有
Outbox 的只读 Probe，还必须由数据库逐字段重建并持久化不可变 authority，之后才用
单条 Lua 原子执行目标 `XADD` 与 legacy fan-out group 的 `XACK`。`queued` 和
`running` Probe 都会转投：后者在目标 PEL 中由平台级 stale recovery 闭环；终态
Bilibili Probe 只有完成幂等 evidence materialization 后才进入终态确认。平台 Probe
终态或无关消息使用 all-groups-confirmed Lua 原子 `XACK`/`XDEL`，只有所有实时 group
都越过精确 ID 且 PEL 不再持有它时才删除。Probe legacy stream 只 `XACK` 并保留作
迁移审计，不在自动排空流程中 `XDEL`。

Account Calibration fan-out 只转投仍为 `queued` 且账号/平台/目标绑定完全一致的
行，并在同一 Lua 中写入短期 provenance marker、目标 `XADD` 和 legacy `XACK`；
平台 Calibration 的终态或无关消息同样只有在所有实时 group 都越过精确 ID 且 PEL
不再持有它时才原子 `XACK`/`XDEL`；legacy stream 只 `XACK`。旧 Worker 与新 lane
同时看到一条请求时，数据库 `queued -> running` CAS 仍保证至多一个执行者取得权限。

控制队列迁移使用独立的
`LEGACY_CONTROL_STREAM_DRAIN_ENABLED`，不能复用任务队列的
`LEGACY_TASK_STREAM_DRAIN_ENABLED`。控制队列也必须按上文停止全部旧 Core/Worker，
完成 Redis bootstrap 与 Schema 迁移后再启动新 Core 和新 Worker；不得采用“先部署
新 Worker、再切换旧 Core producer”的旧滚动步骤。确认 per-platform/legacy Redis
指标、Outbox backlog 和 continuity reconcile 全部
可用且归零后才能关闭 control drain。关闭后保留旧 stream、旧
`adapter-probers` / `account-calibrators` group 和现有 marker 供回滚，不自动做
破坏性清理。Redis ACL 必须覆盖精确平台/legacy stream、continuity 与 marker key，以及
`INFO`、`EVAL`、`GET`、`SET`、`DEL`、`EXPIRE`、`XLEN`、`XADD`、`XACK`、
`XDEL`、`XREADGROUP`、`XCLAIM`、`XPENDING`、`XINFO GROUPS`、
`XINFO CONSUMERS`；继续禁止 runtime group create、flush、group destroy 和
continuity key 越权覆写。
