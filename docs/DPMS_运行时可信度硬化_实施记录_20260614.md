# DPMS 运行时可信度硬化 实施记录（2026-06-14）

## 背景

在 V10–V13 运营规模化主线落地后，一轮深度审阅（《DPMS-Platform 深度审阅报告》）给出的核心判断是：

> 当前最大风险不是功能缺失，而是“运行时可信度不足”。功能已经够多，现在必须停止扩功能，优先做运行时可信度。

审阅按严重度给出 P0 / P1 / P2 三档问题。本记录覆盖据此完成的全部硬化工作，按审阅路线图分阶段推进：**P0 安全修复 → P1 一致性 → real-run 权威门禁合流 → P2 长期演化**。所有改动均先核对真实代码再实施。

测试基线：硬化前 242（V10–V13）→ **294**（本轮净增 52，其中纯逻辑单测覆盖所有可自包含的判定）。本仓库无 DB 集成测试框架，事务/门禁等强依赖 DB 的路径以“纯函数抽取单测 + 严格人工核对”兜底。

## 第 2 阶段：快速 P1 加固（提交 `e6ca6e0`）

低风险、自包含、不动架构的三项：

- **P1-5 Proxy SSRF**：`check_proxy` 的 `target_url` 仅校验 scheme 不够。新增平台域名白名单（bilibili/weibo/douyin/xiaohongshu 及其子域，取自 `PLATFORMS` 的 cookie_domain）；非平台目标需 admin + 确认头。默认目标与现有前端用法不受影响（+11 测试含查找表纯逻辑）。
- **P1-6 通知发送未校验 HTTP 状态**：`send_serverchan/feishu/webhook/telegram` 增加 `raise_for_status()`，对端返回 4xx/5xx 不再被当作成功（+5 测试，mock httpx）。
- **P1-7 Proxy 变更缺审计**：`create/cooldown/check/status` 全部要求 operator 角色并补 `audit_event`+`record_event`，代理 URL 在审计明细中脱敏。

## 第 3 阶段：一致性事务化（提交 `09fdb82`）

### P1-2 派发原子化 + 事务性 outbox

派发原先是三段无共享事务的写：`INSERT task_runs` → `UPDATE lotteries claimed` → `redis.xadd`。进程崩溃或 Redis 短暂不可用时，会留下“已 claimed 但 worker 永远收不到任务”的卡死，或重复点击产生双任务。

- 新增 `outbox_events` 表与 `app.services.outbox`。`dispatch_lottery` 把 `task_runs` 行、抽奖 claim、排队消息（写为 outbox 行）放进**同一个 DB 事务**，提交后再尽力即时投递；Redis 短暂不可用时由 outbox dispatcher 重试（至少一次）。
- 事务内 `SELECT ... FOR UPDATE` 守卫拒绝同一抽奖的重复活动派发；并新增虚拟列 + 唯一索引 `uk_active_task_per_lottery`，从 DB 层兜底“一抽奖至多一个活动任务”。
- 投递采用 `pending → sending → sent` 的 `FOR UPDATE` 认领，确保即时投递与后台循环不会对同一行重复 `xadd`（real-run 任务重复执行的隐患）；崩溃残留的 `sending` 行超时回收，失败行重试到上限。
- `reconcile_orphaned_locks` 在宽限期后释放被终态/缺失任务卡住的抽奖锁。
- `recovery_daemon` 复用统一的 `build_lottery_task_message`，与新派发的字段集严格一致，杜绝漂移。

### P1-3 worker 任务生命周期事务化

`mark_task_started`/`mark_task_finished` 的多表状态写（task_runs / lotteries / accounts [+ notify_logs]）包进 `database.transaction()`；`record_event` 与 Redis 通知改到提交之后，消除“任务成功但抽奖仍 running / 锁未释放”的漂移窗口。

## 第 4 阶段：real-run 权威门禁合流（提交 `a87b1ac`）

### P1-4 Governance 成为唯一 real-run 权威

此前存在两套理念一致但并非同一权威的门禁：派发内联的 `validate_real_run_evidence` 与 Governance 的 policy decision（后者只是审计装饰）。

- 新增 `app.services.real_run_gate`，把门禁统一为：构建账号级 inputs → 加载 active policy → `evaluate_policy`（fail-closed）→ 记录 `policy_decisions` 行 → 仅 `allow` 才能派发。
- `dispatch_lottery` 改为针对**所选账号**调用 `evaluate_real_run_decision`，并把返回的 `decision_id` / `policy_version` 绑定进 `task_runs`（新增可空列；init.sql + ensure_column）。因为 `real_run_gate_status` 本就包裹了 `validate_real_run_evidence`，policy 门禁是旧证据门禁的**严格超集**——合流只会更严，不会更松。
- `governance.py` 删除私有 `_gate_inputs` / `_load_active_policy` 与内联 decision INSERT，统一从 service 导入，API 端与派发端不再可能分叉。
- Semantic trace 展示任务实际绑定的门禁 decision（旧任务回退到该抽奖最近一次 decision）。
- 关键不变量单测：`gate_inputs` 必须覆盖 policy 的每一个 gate code（fail-closed 门禁若有 gate 永远收不到 input 就会永远 block）。

## 第 5 阶段：P2 长期演化（提交 `edc016a`）

- **P2-1 指纹资产隔离一致性**：`ensure_default_fingerprint` 不再把所有账号塞进同一个硬编码指纹。改为 find-or-create 一个由真实、稳定的桌面浏览器画像组成的小池（不同 UA、常见视口、zh-CN/Asia-Shanghai），并把新账号分配给当前绑定最少的画像，使账号分散到不同指纹。强调：这是资产隔离一致性，不是反检测——取值普通且稳定，不伪造异常环境。
- **P2-2 CookieVault 绑定上下文（AES-GCM AAD）**：vault 增加向后兼容的 `aad=` 参数（decrypt 在 AAD 失败时回退到无 AAD 解密，旧密文照常可读）。账号凭据在 core 与 worker 的**全部**加/解密点绑定 `dpms:account-credential`（常量两端逐字节一致）；通知 secret 按 key 绑定 `dpms:notification-secret:<KEY>`。密文不能再被跨用途/跨 key 搬运。注：凭据 AAD 全量启用需 core+worker 协同部署，旧无绑定密文全程经回退可解。
- **P2-3 Event Store 写失败不再静默吞掉**：`record_event` 对瞬时失败重试；`critical=True` 的事件（real-run 派发/拒绝、policy 激活）持久失败时按 ERROR 记录**完整 payload**并落入新的 `failed_events` 死信表以备重放，而不是返回 None 了事。

## 安全不变量（本轮新增/强化）

1. 默认安全：所有 `/api/*` 默认要求 admin token，仅健康探针与 CORS 预检例外。
2. 派发原子 + 至少一次：状态变更与排队消息同事务提交，Redis 入队经 outbox 至少一次且不重复投递。
3. 一抽奖至多一个活动任务：事务内 FOR UPDATE 守卫 + DB 唯一索引双重保证。
4. real-run 唯一权威：仅 Governance policy 的 `allow` 能派发，且每次 real-run 绑定授权它的 decision。
5. 高危审计不丢：critical 事件写失败进死信表 + ERROR 全量日志。
6. 密文绑定用途：凭据与通知 secret 的密文不可跨用途搬运。
