# DPMS 能力演化路线图 v4-v9

## 1. 当前系统定位

当前项目处于 **V3 Execution Runtime** 阶段，本质是一个以执行、监控和恢复为核心的 DPMS Runtime。

现有核心结构：

- `core/app`：后端 API、配置、数据库、安全门禁、平台配置。
- `worker/app`：任务消费、适配器执行、账号校准、证据记录。
- `worker/app/adapters`：平台适配器与执行探针。
- `frontend/src`：Runtime Console 前端控制台。
- `dashboard/dist`：前端生产构建产物。
- `docker-compose.yml`：MySQL、Redis、Core API、Worker、Nginx 一键启动编排。

当前系统能力：

- 发现：支持活动源、目标导入、手动录入。
- 执行：支持 dry-run、real-run 门禁、Worker 消费。
- 监控：支持 Worker 心跳、生产门禁、平台就绪度、任务记录。
- 恢复：支持失败证据、通知、回滚入口、运行时安全开关。
- 登录：支持二维码登录会话与 Cookie 凭据导入。
- 安全：支持管理员令牌、确认头、审计日志、熔断器、real-run 全局开关。

当前完成度评估：**75%**。

主要缺失能力：

- 记忆：系统不能完整回答账号、活动、风险、策略的长期历史。
- 知识：历史数据尚未被提炼为平台画像、奖品画像、账号画像和风险画像。
- 学习：缺少可训练的特征存储和概率模型。
- 实验：缺少策略 A/B/C 并行验证和自动评估。
- 制度：策略仍偏过程代码，尚未制度对象化、版本化和可追溯。

## 2. 演化原则

后续规划不按功能模块堆叠，而按系统能力演化推进。

目标演化链路：

```text
Execution Runtime
-> Data Runtime
-> Knowledge Runtime
-> Strategy Runtime
-> Learning Runtime
-> Governance Runtime
-> Semantic Runtime
```

安全边界：

- “反爬与账号安全”在本项目中定义为 **合规限速、账号隔离、风险预测、触发验证码或平台审核时停止并通知**。
- 系统不得设计为绕过验证码、隐藏真实自动化行为、规避平台风控或突破第三方服务条款的工具。
- real-run 必须继续保留管理员授权、确认动作、熔断器、证据记录和审计日志。

| 版本 | 名称 | 核心能力 | 预计周期 | 首要产出 |
| --- | --- | --- | --- | --- |

| V6.5 | Learning Runtime | 学习 | 2 个月 | Feature Store、中奖概率模型、风险概率模型 |

优先投入顺序：

```text
Event Store

-> Risk Intelligence
-> Learning Runtime
```

## 4. V4.0 Event Driven Runtime

预计周期：**1-2 个月**。

### 4.1 当前问题

当前执行链路大体为：

```text
任务执行
-> 结果写数据库
-> 结束
```

系统可以看到当前状态，但无法稳定回答长期历史问题，例如：

- 账号 A 过去一年参加过多少活动。
- 账号 A 过去一年中奖多少次。
- 账号 A 触发过多少次验证码。
- 账号 A 被冷却、封禁、限流过多少次。
- 某个平台在不同奖品类型下的中奖率变化。
- 某个代理出口关联过多少风险事件。

### 4.2 改造目标

新增事件存储能力，建议目录：

```text
core/app/event_store/
worker/app/event_store/
frontend/src/pages/EventTimeline.jsx
```

建议逻辑结构：

```text
event_store
├── account_events
├── lottery_events
├── risk_events
├── browser_events
├── strategy_events
├── system_events
└── governance_events
```

统一事件模型：

```json
{
  "id": "uuid",
  "aggregate": "account",
  "aggregate_id": "account-001",
  "event_type": "captcha_triggered",
  "payload": {},
  "timestamp": "2026-06-05T00:00:00Z"
}
```

数据库建议表：`events`。

参数超过 3 个时采用统一表结构：

| 参数名 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | string | 是 | 无 | 事件 UUID |
| `aggregate` | string | 是 | 无 | 聚合类型，例如 `account`、`lottery`、`risk` |
| `aggregate_id` | string | 是 | 无 | 聚合实体 ID |
| `event_type` | string | 是 | 无 | 事件类型 |
| `payload` | json | 否 | `{}` | 事件详情 |
| `correlation_id` | string | 否 | `null` | 关联一次任务、一次请求或一次工作流 |
| `causation_id` | string | 否 | `null` | 触发当前事件的上游事件 |
| `actor_type` | string | 否 | `system` | 操作者类型 |
| `actor_id` | string | 否 | `null` | 操作者 ID |
| `timestamp` | datetime | 是 | 当前时间 | 事件发生时间 |

### 4.3 事件分类

Account：

- `AccountCreated`
- `AccountLogin`
- `AccountLogout`
- `AccountCredentialImported`
- `AccountCalibrated`
- `AccountCooling`
- `AccountSuspended`
- `AccountDeleted`

Lottery：

- `LotteryDiscovered`
- `LotteryScored`
- `LotteryJoined`
- `LotteryWon`
- `LotteryLost`
- `LotterySkipped`
- `LotteryExpired`

Risk：

- `CaptchaTriggered`
- `RateLimited`
- `ShadowBanned`
- `ReviewRejected`
- `RiskScoreChanged`
- `CircuitBreakerOpened`
- `CircuitBreakerClosed`

Browser：

- `BrowserCreated`
- `BrowserDestroyed`
- `FingerprintChanged`
- `SessionExpired`
- `QrLoginRequested`
- `QrLoginCompleted`

Strategy：

- `StrategyApplied`
- `StrategyEvaluated`
- `StrategyRetired`
- `StrategyOverridden`

System：

- `WorkerStarted`
- `WorkerHeartbeat`
- `TaskDispatched`
- `TaskStarted`
- `TaskFinished`
- `TaskFailed`
- `NotificationSent`
- `NotificationFailed`

Governance：

- `PolicyCreated`
- `PolicyActivated`
- `PolicyRetired`
- `PolicyViolationDetected`
- `RealRunApproved`
- `RealRunDenied`

### 4.4 V4 最小可落地范围

第一轮只做事件采集，不急于做复杂分析。

必须接入的事件源：

- 账号创建、Cookie 导入、二维码登录、账号删除。
- 抽奖目标导入、任务派发、任务开始、任务完成、任务失败。
- Worker 心跳、熔断器变化、real-run 授权拒绝。
- 通知发送成功和失败。
- 风险事件写入。

必须新增的接口：

- `GET /api/events`
- `GET /api/events/{id}`
- `GET /api/accounts/{account_id}/events`
- `GET /api/lotteries/{lottery_id}/events`
- `GET /api/tasks/{task_id}/events`

必须新增的前端视图：

- 事件时间线。
- 账号详情事件历史。
- 任务详情执行链路。
- 风险事件关联上下文。

V4 收益：系统获得长期记忆。

## 5. V4.5 Knowledge Runtime

预计周期：**2 个月**。

### 5.1 改造目标

新增知识运行时，建议目录：

```text
core/app/knowledge/
worker/app/knowledge/
frontend/src/pages/Knowledge.jsx
```

从事件历史中提炼以下知识：

- Lottery Knowledge：平台、奖品、参与人数、中奖率、奖品可信度。
- Risk Knowledge：账号、IP、设备、代理、验证码、封禁、审核拒绝之间的关系。
- Platform Knowledge：不同平台的规则偏好和风险特征。

### 5.2 Lottery Knowledge

示例：

```json
{
  "platform": "bilibili",
  "prize": "steam",
  "sample": 12000,
  "win_rate": 0.042
}
```

核心字段：

| 参数名 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `platform` | string | 是 | 无 | 平台 |
| `prize_type` | string | 是 | 无 | 奖品类型 |
| `sample` | integer | 是 | `0` | 样本数 |
| `win_count` | integer | 是 | `0` | 中奖次数 |
| `win_rate` | float | 是 | `0` | 中奖率 |
| `trust_score` | float | 是 | `0.5` | 活动可信度 |
| `updated_at` | datetime | 是 | 当前时间 | 更新时间 |

### 5.3 Platform Profile

示例画像：

- Bilibili：评论权重较高，动态互动链路需要更严格的账号健康检查。
- Weibo：转发权重较高，传播行为频率需要更保守。
- Xiaohongshu：内容质量权重较高，低质量重复文本风险更高。
- Douyin：会话和设备状态更敏感，应优先 dry-run 探针。

V4.5 收益：系统开始拥有经验。

## 6. V5 Strategy Runtime

预计周期：**2 个月**。

### 6.1 改造目标

新增策略运行时，建议目录：

```text
core/app/strategy/
worker/app/strategy/
frontend/src/pages/Strategy.jsx
```

当前流程：

```text
发现
-> 参加
```

目标流程：

```text
发现
-> 评估
-> 排序
-> 选择
-> 派发
```

### 6.2 Lottery Strategy

基础评分模型：

```text
Expected Value
= Prize Value
× Win Probability
× Trust Score
```

策略输入：

- 平台。
- 奖品价值。
- 奖品类型。
- 活动可信度。
- 预计中奖率。
- 账号可用性。
- 平台风险水平。
- 执行动作复杂度。
- 过期时间。

策略输出：

- 是否参与。
- 参与优先级。
- 推荐账号等级。
- 推荐执行模式：`dry-run`、`shadow-run`、`real-run`。
- 风险说明。

### 6.3 Account Strategy

账号分层：

- S 级账号：高健康度、高可信、低风险历史，用于高价值抽奖。
- A 级账号：稳定账号，用于中等价值抽奖。
- B 级账号：普通账号，用于低价值或探针任务。
- 冷却账号：不可派发真实任务。
- 需登录账号：不可派发，必须重新校准。

### 6.4 Resource Strategy

资源策略决定以下绑定关系：

- 账号。
- 代理出口。
- 浏览器会话。
- 平台。
- 活动目标。
- 执行时间窗口。

V5 收益：系统开始思考。

## 7. V5.5 Experiment Runtime

预计周期：**1 个月**。

### 7.1 改造目标

新增实验运行时，建议目录：

```text
core/app/experiment/
worker/app/experiment/
frontend/src/pages/Experiment.jsx
```

支持策略 A/B/C 并行运行，并将实验结果写回事件与知识库。

示例：评论策略实验。

- Policy A：短祝福评论。
- Policy B：中性好运评论。
- Policy C：更长的上下文评论。

系统统计：

- 参与次数。
- 中奖次数。
- 审核失败次数。
- 验证码触发次数。
- 账号风险变化。
- 平台差异。

### 7.2 实验约束

- 实验默认只允许 dry-run 或 shadow-run。
- real-run 实验必须经过管理员授权和策略门禁。
- 触发验证码、限流、审核拒绝时自动停止对应实验分支。
- 不允许生成垃圾内容或高频重复内容。

V5.5 收益：经验开始增长。

## 8. V6 Risk Intelligence

预计周期：**2 个月**。

### 8.1 改造目标

将当前 Risk Engine 升级为 Risk Intelligence。

新增对象：

- Device Reputation：设备信誉分。
- Account Reputation：账号信誉分。
- Proxy Reputation：代理信誉分。
- Platform Risk Profile：平台风险画像。
- Risk Forecast：未来 24 小时风险预测。

### 8.2 风险预测输出

| 参数名 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `account_id` | string | 是 | 无 | 账号 ID |
| `platform` | string | 是 | 无 | 平台 |
| `risk_score` | float | 是 | `0` | 当前风险分 |
| `forecast_24h` | float | 是 | `0` | 未来 24 小时风险概率 |
| `risk_reasons` | array | 否 | `[]` | 风险原因 |
| `recommended_action` | string | 是 | `hold` | 推荐动作 |

推荐动作：

- `allow`
- `dry_run_only`
- `cooldown`
- `relogin`
- `manual_review`
- `block`

V6 收益：系统开始预测，而不是只在事故发生后处理。

## 9. V6.5 Learning Runtime

预计周期：**2 个月**。

### 9.1 改造目标

建立 Feature Store。

建议目录：

```text
core/app/learning/
worker/app/learning/
```

记录特征：

- 账号年龄。
- 账号等级。
- 评论长度。
- 活动类型。
- 参与时间。
- 奖品价值。
- 平台。
- 代理信誉。
- 设备信誉。
- 最近风险事件数量。

学习目标：

- Win Probability Model：中奖概率模型。
- Risk Probability Model：风险概率模型。

### 9.2 上线约束

- 模型只提供建议，不直接越过 real-run 门禁。
- 模型版本必须记录。
- 模型输入特征必须可解释。
- 任何模型导致的派发决策必须可回放。

V6.5 收益：系统开始学习。

## 10. V7 Governance Runtime

预计周期：**3 个月**。

### 10.1 改造目标

新增制度运行时，建议目录：

```text
core/app/institution/
worker/app/institution/
frontend/src/pages/Governance.jsx
```

制度对象示例：

```json
{
  "institution": "risk_policy",
  "version": "7.2",
  "status": "active"
}
```

目标是让策略不再散落为过程代码，例如：

```text

```

而是统一变成可版本化、可审计、可回滚的 Policy Object。

V7 收益：系统行为开始制度化。

- 新策略版本。

## 12. V9 Semantic Runtime

预计周期：**6-12 个月**。

### 12.1 最终目标

形成完整语义执行链：

```text
Intent
-> Institution
-> Policy
-> Transition
-> Execution
```

此阶段目标不是扩大执行量，而是让系统能够将目标、制度、策略、迁移和执行统一建模。

V9 收益：系统从抽奖自动化程序演化为具备自我解释、自我约束和自我改进能力的自治运行时。

## 13. 近期执行计划

### 13.1 0-30 天

优先完成 V4 Event Store 最小闭环。

任务清单：

1. 新增 `events` 数据表与迁移逻辑。
2. 新增 `core/app/event_store` 事件写入服务。
3. 在账号、任务、通知、风险、Worker 心跳中接入事件写入。
4. 新增事件查询 API。
5. 新增前端事件时间线页面。
6. 将已有审计日志与事件日志建立关联，不强行合并。

验收标准：

- 任意一次任务派发可以回放完整事件链。
- 任意账号可以查看历史登录、校准、风险、任务参与记录。
- 任意失败任务可以看到失败前后的上下文事件。

任务清单：

1. 基于事件聚合平台画像。

任务清单：

- `core/app/main.py`：短期继续负责表初始化，后续应拆迁移脚本。
- `worker/app/task_runner.py`：继续负责执行闭环，但需要发出事件。
- `worker/app/adapters`：继续负责平台动作实现，但不承载策略决策。
- `frontend/src/pages`：继续按运行时能力拆页面，不再只按原始功能拆页面。

## 15. 决策结论

从当前代码库出发，最值得投入的不是继续堆更多平台 Adapter 或更多账号数量，而是先完成以下六步：

```text
Event Store
-> Knowledge Runtime
-> Strategy Runtime
-> Experiment Runtime
-> Risk Intelligence
-> Learning Runtime
```

这六步完成后，系统才会从“执行预先写好的流程”转向“积累经验并利用经验做决策”。
