# DPMS 后续开发总设计方案 v1（2026-06-11）

## 0. 文档定位

本文是 DPMS-Platform 的**后续开发总设计方案**，在 `docs/DPMS_能力演化路线图_v4-v9_20260605.md` 的长期愿景之上，对照当前真实代码状态重新校准优先级，给出可执行、可验收、安全边界明确的分阶段计划。

- 路线图（v4-v9）回答“最终要演化成什么”。
- 本总方案回答“从今天的代码出发，下一步怎么走，怎么验收”。
- 每个阶段都给出**验收标准**与**安全约束**，不允许为了推进进度而突破安全边界。

## 1. 安全边界（不可协商，逐字保留）

> 「反爬与账号安全」在本项目中仅指合规限速、风险识别、账号隔离和触发验证码/审核时停止并通知，不用于绕过验证码或规避平台保护机制。

由此派生的硬约束，任何阶段都必须满足：

- real-run 必须继续保留：管理员授权、确认动作、熔断器、证据记录、审计日志、全局开关。
- 策略层只能**建议**执行模式与排序，不得自动越过 real-run 门禁。
- 触发验证码、限流、审核拒绝时，必须停止对应分支并通知，不得隐藏或绕过。
- 任何模型/策略导致的派发决策必须可解释、可回放。

路线图当时评估完成度 75%（V3 Execution Runtime）。截至本方案，系统实际已显著超出该阶段：

| --- | --- | --- | --- |

| 策略运行时（决策） | V5 | 🟡 建议级已落地 | `GET /api/lotteries/strategy/queue`（期望值评分、模式选择、账号信誉） |
| 多平台适配 | — | 🟡 校准阶段 | `worker/app/adapters/{bilibili,weibo,xiaohongshu,douyin}.py`，均 `calibration_required` |

**结论**：系统的“执行—记忆—经验”三层已经成型，“决策”层以只读建议形式存在但尚未模块化、未被测试覆盖。真正的瓶颈不是再堆平台或账号，而是：

1. 决策层（Strategy Runtime）仍以过程代码散落在 API 文件中，未制度对象化、无单元测试。
2. **Worker 侧长期零自动化测试**（历次实施记录反复标注的工程缺口）。
3. 知识/策略尚未在前端形成独立可视化页面（仅嵌在 Dashboard 与 Lotteries 中）。
4. 各平台真实选择器仍需人工探针校准（这是**有意的人工关卡**，非缺陷）。

```text
            ┌──────────────────────── Runtime Console (React/Vite) ────────────────────────┐
            │ Dashboard │ Accounts │ Lotteries │ Tasks │ Events │ Risk │ Deploy             │
            └───────────────────────────────────┬──────────────────────────────────────────┘
                                                 │ /api（Nginx 反代）
        ┌────────────────────────────────────────┴───────────────────────────────────────┐
        │ core-api (FastAPI)                                                               │
        │  accounts / lotteries / notify / proxies / metrics / events / knowledge          │
        │  security（管理员令牌·确认头·熔断器·审计·real-run 开关）                            │
        │  strategy/engine（V5 纯决策）   knowledge/{service,scoring}（V4.5 画像与评分）       │
        │  event_store（V4 统一事件）     services（discovery/rules/scheduler/risk/...）       │
        └───────────────┬─────────────────────────────────────────────┬────────────────────┘
                        │ MySQL（状态/事件/证据/审计）                  │ Redis（任务流/通知流/校准流）
        ┌───────────────┴─────────────────────────────────────────────┴────────────────────┐
        │ worker (Playwright)                                                               │
        │  task_runner（dry/shadow/real 闭环）  safety（限速·风险停止）  adapters（四平台）     │
        │  login_broker（扫码登录）  account_calibrator（登录校准）  adapter_probe（只读探针）  │
        └───────────────────────────────────────────────────────────────────────────────────┘
```

数据主链路（目标工作流）：

```text
发现 → 解析规则 → 评估价值/风险 → 选择账号 → 排程
→ probe / dry-run / shadow-run → 安全门禁 → real-run → 证据保存 → 通知 → 复盘 → 策略建议
```

## 4. 总设计方案：后续分阶段计划

总原则：**先把已有能力收口、测稳、可视化，再向上演化。** 每阶段都应能独立验收并保持系统可回滚。

### 阶段 S1（本次启动）：Strategy Runtime 模块化 + 工程质量基线

目标：把决策层从“过程代码”变成“可测试的制度对象”，并补齐测试基线。

- S1.1 抽取纯策略引擎到 `core/app/strategy/engine.py`（无 DB 依赖）。✅ 本次完成
- S1.2 抽取知识评分到 `core/app/knowledge/scoring.py`（无 DB 依赖）。✅ 本次完成
- S1.3 新增策略引擎与知识评分单元测试（core）。✅ 本次完成
- S1.4 建立 **worker 测试基线**（首次）。✅ 本次完成
- S1.5 引入 S/A/B 优先级分层（活动）与账号分层（路线图 §6.3）。✅ 本次完成

验收标准：

- 决策/评分逻辑可在无数据库环境下 `python -m unittest` 全量通过。
- worker 目录存在可运行测试。
- `strategy/queue` 输出新增 `priority_tier`，账号建议新增 `account_tier`，不改变既有字段语义。

### 阶段 S2：决策可解释 + 前端 Strategy/Knowledge 页面

目标：把已有的 `strategy/queue` 与 `knowledge/summary` 数据转化为操作员可读的独立页面，并让每条建议“可解释”。

- 新增 `GET /api/lotteries/{id}/strategy/explain`：返回单个目标的评分构成（模式选择原因、期望值分解、风险扣分、知识置信度来源）。
- 新增前端 `Strategy.jsx`：策略队列（按 `priority_tier` 分组）+ 单目标解释抽屉。
- 新增前端 `Knowledge.jsx`：数据成熟度、平台/账号画像、学习缺口清单（复用 `knowledge/summary`）。
- 不引入任何自动派发；页面仅展示建议，派发仍走现有人工确认流程。

验收标准：四平台均能在 Strategy/Knowledge 页看到画像与建议；每条建议可展开查看评分构成；real-run 仍需人工确认。

### 阶段 S3：Experiment Runtime 最小闭环（路线图 V5.5）

目标：在 dry-run / shadow-run 范围内支持评论/时段等策略的 A/B 对比，并把结果写回事件与知识库。

- 新增 `experiments` 表与 `core/app/experiment/`：实验定义、分支、样本统计。
- 实验默认仅允许 dry-run / shadow-run；real-run 实验必须管理员授权 + 策略门禁。
- 触发验证码/限流/审核拒绝时自动停止对应分支（复用 `safety.py` 信号）。
- 禁止生成垃圾内容或高频重复内容（评论内容来自受控模板池）。

验收标准：能并行运行 ≥2 个策略分支并产出参与/中奖/风险对比；任一风险信号能自动停止对应分支并通知。

### 阶段 S4：Risk Intelligence（路线图 V6）

目标：把 `risk_engine` 升级为带预测的风险情报，新增账号/设备/代理信誉与 24 小时风险预测。

- 复用现有 `risk_events` 与 `proxies`，新增信誉聚合与 `forecast_24h` 输出。
- 推荐动作限定为安全集合：`allow / dry_run_only / cooldown / relogin / manual_review / block`。
- 预测只用于**收紧**派发（更保守），不得用于放宽 real-run 门禁。

验收标准：每个账号能给出当前风险分与 24h 预测和推荐动作；预测仅能让策略更保守。

### 阶段 S5+：Learning / Governance / Transition / Semantic（路线图 V6.5–V9）

保持路线图既定顺序与安全约束推进：Feature Store → 概率模型（仅建议）→ Policy Object 制度化 → 策略迁移图 → 语义执行链。每一步都必须满足“模型只建议、版本可记录、特征可解释、决策可回放”。

## 5. 工程质量基线（横切所有阶段）

S1 已确立以下基线，后续阶段必须维持：

- **纯逻辑与数据访问分离**：新决策/评分逻辑写在无 DB 依赖的纯模块中，便于单测。
- **测试随功能落地**：core 与 worker 均维护可运行测试；纯函数必须有单测。
- **行为保持式重构**：抽取/搬迁不得改变既有 API 字段语义；新增字段而非修改。
- **本机可验证**：`py_compile` + `unittest` + `npm run build` 构成最低验证集（无需数据库即可跑纯逻辑测试）。

当前测试覆盖（本次后）：

- core：`test_lottery_targets`、`test_canonicalizer`、`test_bilibili_discovery`、`test_bilibili_qr`、`test_lottery_rules`、`test_strategy_engine`、`test_knowledge_scoring` —— 共 94 项通过。
- worker：`test_adapter_config` —— 21 项通过（worker 首个测试集）。

## 7. 风险与已知限制

- 本方案的 S2 及以后阶段尚未实现，仅为设计与验收契约。
- 各平台真实选择器仍需人工探针校准（有意的人工关卡）。
