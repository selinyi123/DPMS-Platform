# DPMS Bilibili 官方二维码登录实施记录

## 问题

原二维码登录由 Worker 打开整张平台登录网页并周期性截图。该方案存在以下工程问题：

- 截图不是稳定的二维码资源，页面结构变化会导致二维码不可见。
- 前端可能重复显示旧截图，扫码状态缺少明确语义。
- Cookie 导入只验证格式，不验证平台必需字段。
- 账号校准主要依据 Cookie 名称存在，无法证明 Bilibili 身份仍有效。

## 实现

- Bilibili 登录改为官方二维码生成与轮询协议。
- 二维码由前端使用固定版本 `qrcode@1.5.4` 本地渲染，不经过第三方二维码服务。
- 登录会话支持 `waiting_scan`、`scanned`、`confirmed`、`expired` 和 `failed` 状态。
- 临时轮询网络错误不会立即作废会话；会话继续等待，直到恢复、确认或三分钟过期。
- 官方 `qrcode_key` 仅保存在数据库，不通过 API 返回前端。
- 扫码确认后仅提取 Bilibili 登录 Cookie，加密写入账号凭据并自动排入校准。
- 若扫码确认后校准队列临时不可用，账号仍会保留，界面显示错误并允许人工重试校准。
- Cookie 创建和更新接口必须包含平台配置声明的必需 Cookie。
- Bilibili 校准新增 `nav` 身份检查，只有 `isLogin=true` 且存在 `mid` 才可进入 `ready`。
- 管理员令牌不再从 `localStorage` 回填到输入框，降低截图和 DOM 快照泄露风险。
- 移动端侧栏设置改为折叠区，账号登录页更早进入首屏。
- Weibo、Douyin、Xiaohongshu 暂时保留原浏览器登录代理，不受本次变更影响。

## 安全边界

- 二维码只能由用户使用 Bilibili 官方 App 扫描并在手机端确认。
- 系统不自动填写密码、不绕过验证码，也不规避平台登录保护。
- 未扫码、已过期或不完整 Cookie 不会创建可用账号。
- Real-run 门禁保持关闭，不因登录成功自动开启。

## 验证

- Bilibili 官方生成接口返回二维码 URL 和 key。
- 未扫码轮询返回 `waiting_scan`，账号数量保持不变。
- API 响应不包含 `provider_key`。
- 缺少 `SESSDATA`、`DedeUserID` 的 Cookie 返回 HTTP 400。
- 8 个 Python 单元测试通过。
- 前端生产构建通过。
- 生产前端依赖审计为 0 个已知漏洞。
- 桌面二维码渲染尺寸为 `320 × 320`，无拉伸。
- `390px` 手机视口无横向溢出。
- 浏览器控制台 0 个错误、0 个警告。

## 待用户完成
