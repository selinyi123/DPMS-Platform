# DPMS_V10-V13_运营规模化_后续版本规划_v1.0_20260614

## 文档定位

`docs/DPMS_能力演化路线图_v4-v9_20260605.md` 规划的 V4–V9（Event / Knowledge / Strategy / Experiment / Risk Intelligence / Learning / Governance / Transition / Semantic）九个里程碑均已落地（详见各实施记录与 [[DPMS_V9_SemanticRuntime_实施记录_20260613]]）。V4–V9 是一条**认知阶梯**：让系统能记忆、提炼、决策、实验、预测、学习、制度化、留痕演化、自我解释。

本文档规划**下一条主线 —— 运营规模化（Operational Scaling）**，对应 **V10–V13** 四个重量级大版本。与 V4–V9 的「认知层」不同，V10–V13 聚焦**执行层的有序放大**：在**不触碰任何安全边界**的前提下，把「单目标、单账号、手工排程」升级为「跨平台、批量账号、可持续吞吐」的有序编排。

> **核心立场（不可协商）**：本主线所说的「规模化」是**有序地、合规地组织执行**，**绝不是**提高对平台风控的冲击。所有新增层与 V4–V9 完全一致：**只读、advisory、零新增决策权**。具体而言：
> - 一切「计划/建议」都是**草案**，真实派发仍**只能**经由既有 real-run 门禁（V7 `evaluate_policy`）+ 管理员授权 + 熔断器；新层从不自动派发、不自动激活、不写决策路径。
> - 限速一律是**合规限速**（平台友好的保守上限），引擎只会让执行**更保守**（withhold / throttle），**永不**放宽或绕过限速、验证码、风控。
> - **账号隔离**（1 账号 : 1 代理 : 1 指纹）是一等公民：V11 只**检测并告警**隔离冲突，从不制造共享。
> - **强制安全爬坡**：V12 编排的每一波次必须遵循 `dry_run -> shadow_run -> real_run` 阶梯，不得跳级。
> - **背压只会减速**：V13 的吞吐治理只在风险上升时建议**降速/暂停**，是「刹车」而非「油门」。

**前置事实**（V10–V13 设计的数据基础，均已存在）：

- `accounts(id, platform, fingerprint_id, proxy_id[1:1 UNIQUE], status, risk_score, daily_task_count, last_active_at)`
- `proxies(id, proxy_url, health_score, cooldown_until, status)`、`fingerprints(id, platform, ...)`
- `lotteries(id, platform, status, value_score, expires_at)`
- `task_runs(id, task_id, account_id, lottery_id, status[queued/running/succeeded/failed], dry_run, task_mode, created_at, started_at, finished_at)`
- `risk_events`（V6 风险来源）、V5 策略评分、V6 `account_risk_intelligence`、V7 `policy_decisions` / 门禁状态。

## 总体里程碑

| 版本 | 名称 | 核心能力 | 「规模化」动词 | 是否新增表 |
| --- | --- | --- | --- | --- |
| V10 | Scheduling Runtime（调度运行时） | 规划**何时**执行：账号冷却、合规限速、时间窗、最小间隔 | 编排时间 | 否（纯聚合） |
| V11 | Capacity Runtime（容量运行时） | 建模**供给**：安全账号/代理/会话、可持续上限、隔离绑定建议 | 编排资源 | 否（纯聚合） |
| V12 | Orchestration Runtime（编排运行时） | **跨平台批量**编排成分波次（waves），强制安全爬坡 | 编排广度 | 是（`campaign_plans` 草案审计） |
| V13 | Throughput Runtime（吞吐运行时） | 可持续吞吐**治理器** + 背压：风险上升只建议降速 | 守住可持续 | 否（纯聚合） |

阶梯关系：**V10 何时 → V11 用什么 → V12 跨平台成批协调 → V13 守住可持续**。V13 是收口的「治理器」，确保前三者放大的负载始终落在可持续区间内。

## V10：Scheduling Runtime（调度运行时）

### 目标

把「何时派发」从隐式的人工节奏，变成一个**显式、合规、可解释的排程计划**：在给定时间窗内，为候选目标分配执行时隙，严格遵守**每账号日上限、最小任务间隔、账号冷却、平台并发上限**。计划是**建议**，真实派发仍走门禁。

### 建议目录

```text
core/app/scheduling/
  __init__.py
  engine.py        # 纯逻辑：限速表、配额、排程、限速自检、过载检测
core/app/api/scheduling.py
core/tests/test_scheduling_engine.py
frontend/src/pages/Scheduling.jsx
```

### 数据结构（`engine.py`，无 DB，时间用「相对 now 的分钟偏移」表达以保持纯函数）

- `PLATFORM_RATE_LIMITS`：每平台 `{max_daily_per_account, min_spacing_min, max_per_window}` 的**保守默认**；`DEFAULT_RATE_LIMIT` 作回退；`rate_limit_for(platform)`。
- `plan_schedule(*, candidates, accounts, window_minutes, limits=None) -> dict`：
  - `candidate = {lottery_id, platform, value_score}`；`account = {account_id, platform, remaining_quota, ready_in_min, risk_score}`（仅传入可派发账号；引擎再按 `remaining_quota>0` 过滤）。
  - 按平台分组；候选按 `(value_score desc, lottery_id asc)`；账号按 `(ready_in_min asc, remaining_quota desc, risk_score asc)`。逐候选挑「最早可用且仍有配额」的账号，分配 `scheduled_at_offset_min = next_free`，随后该账号 `next_free += min_spacing_min`、`quota_left -= 1`。
  - 超窗 / 配额耗尽的候选进入 `unscheduled`，附 `reason`。
  - 返回 `{window_minutes, slots:[...], unscheduled:[...], summary:{planned, unscheduled, per_platform:{...}}}`。
- `respects_rate_limit(plan, limits) -> (bool, violations)`：自检——每账号分配数 ≤ 配额、相邻时隙间隔 ≥ `min_spacing_min`、`scheduled_at_offset < window`。供测试与安全断言。
- `detect_overload(candidates, accounts, limits) -> list[str]`：需求 > 窗内可持续供给的平台清单。

### API（`/api/scheduling`，只读）

- `GET /plan?window_minutes=120&platform=`：加载 `status='ready'` 账号（含 `daily_task_count`/`last_active_at`/`risk_score`）与 `pending|claimed` 未过期候选；由 `last_active_at` 与 `min_spacing_min` 计算 `ready_in_min`、由 `max_daily_per_account - daily_task_count` 计算 `remaining_quota`；调用 `plan_schedule`，把分钟偏移转回 ISO 时间戳返回。
- `GET /limits`：透明返回各平台合规限速表。
- 全程零写。`mode` 字段标注为 `"gated"`，明示「真实执行模式由 real-run 门禁在派发时决定」，排程层不决定 mode。

### 安全边界

排程层只会在「超限」时**留空（unscheduled）**，**永不**安排超过合规限速的任务；不派发、不写库；`respects_rate_limit` 作为不变量回归测试。

### 验收标准

- 给定一批候选与若干 ready 账号，`GET /scheduling/plan` 能返回每账号不超日配额、相邻间隔达标、全部落在窗内的时隙表，超出部分进入 `unscheduled` 并带原因。

## V11：Capacity Runtime（容量运行时）

### 目标

把**供给侧**显式化：每平台有多少安全账号 / 健康代理 / 可用会话，可持续日吞吐上限是多少，并给出**遵守隔离**的「账号 ↔ 代理 ↔ 平台」绑定建议。**检测隔离冲突**（共享代理/指纹）并告警——这是 V11 的核心安全产出。

### 建议目录

```text
core/app/capacity/
  __init__.py
  engine.py        # 纯逻辑：容量聚合、可持续上限、绑定建议、隔离冲突检测
core/app/api/capacity.py
core/tests/test_capacity_engine.py
frontend/src/pages/Capacity.jsx
```

### 数据结构（`engine.py`，无 DB）

- `compute_capacity(accounts, proxies, *, limits) -> {platform: {safe_accounts, healthy_proxies, sustainable_daily, headroom, ...}}`：`sustainable_daily = safe_accounts * max_daily_per_account`，并以健康代理数 / 窗口×间隔做二次封顶。
- `recommend_bindings(accounts, proxies, *, existing_bindings) -> [{account_id, proxy_id, platform, status}]`：在**一账号一代理**约束下，为缺代理的 ready 账号建议空闲健康代理；从不建议共享。
- `isolation_violations(accounts) -> [{kind, ids, detail}]`：检测多账号共享同一 `proxy_id` 或 `fingerprint_id`（应为空；非空即隔离风险，醒目告警）。

### API（`/api/capacity`，只读）

- `GET /overview`：每平台供给与可持续上限、headroom。
- `GET /bindings`：绑定建议 + `isolation_violations`。
- 零写：绑定只是**建议**，实际绑定仍由既有账号管理流程人工执行。

### 安全边界

账号隔离是不变量：引擎只检测/建议，**从不**制造共享绑定；`isolation_violations` 非空时前端醒目标红。

### 验收标准

- 构造共享代理的账号样本，`isolation_violations` 能精确指出冲突；正常样本返回空。
- `compute_capacity` 的 `sustainable_daily` 不超过「安全账号数 × 合规日上限」。

## V12：Orchestration Runtime（编排运行时）

### 目标

把 V10（何时）+ V11（用什么）合成**端到端的跨平台批量计划**：给定跨多平台的一批目标，产出**分波次（waves）的协调执行计划**，每波遵守平台限速、容量上限与**强制安全爬坡**（`dry_run -> shadow_run -> real_run`，不得跳级）。计划是**草案**，落库仅供审计，**绝不自动执行**。

### 建议目录

```text
core/app/orchestration/
  __init__.py
  engine.py        # 纯逻辑：波次规划、爬坡校验、批量风险摘要
core/app/api/orchestration.py
core/tests/test_orchestration_engine.py
frontend/src/pages/Orchestration.jsx
```

### 数据结构（`engine.py`，无 DB）

- `RAMP_STAGES = ("dry_run", "shadow_run", "real_run")`。
- `build_campaign_plan(*, targets, capacity, *, ramp_policy) -> {waves:[...], summary}`：把目标按平台与价值分配到波次；每个目标的**首波 mode 不得高于其已达成的爬坡阶段**；高价值/高风险目标爬坡更保守。
- `validate_campaign(plan, *, gate_state) -> (valid, errors)`：任何包含 `real_run` 的波次，其目标必须在 `gate_state` 中为「门禁通过」；未完成 shadow 的目标不得进入 real_run 波次（镜像门禁，绝不绕过）。
- `campaign_risk_summary(plan) -> dict`：每平台负载、波次数、爬坡分布、需复核项。

### API（`/api/orchestration`，只读 + 草案落库）

- `GET /campaign?...`：依据当前容量/门禁状态生成计划（**不写**）。
- `POST /campaign/draft`（admin）：将一份生成的计划存为 `campaign_plans`（`status='draft'`，**永不**自动变 `active`/执行），供审计与人工对照；采纳仍需走既有派发流程。
- 新增表 `campaign_plans(id, campaign_key, platform_scope JSON, plan JSON, status['draft'], waves INT, requires_review TINYINT, created_by, created_at)`，幂等 `CREATE TABLE IF NOT EXISTS`。

### 安全边界

计划永远是 `draft`；强制爬坡不可跳级；`validate_campaign` 复用 real-run 门禁状态作为 real 波次的唯一准入；落库的草案是**惰性**对象，不接入任何执行路径。

### 验收标准

- 给定跨 2+ 平台的目标集，生成的波次每波不超容量、real 波次仅含门禁通过目标；构造「未 shadow 即 real」的非法计划，`validate_campaign` 报错。

## V13：Throughput Runtime（吞吐运行时）

### 目标

收口的**可持续吞吐治理器**：持续度量「实际负载 vs 可持续上限」，在接近不安全利用率（限速饱和、风险事件上升、逼近熔断）时给出**背压建议**——只会建议 `hold / throttle / pause`（降速方向），让前三版放大的规模**安全落地**。

### 建议目录

```text
core/app/throughput/
  __init__.py
  engine.py        # 纯逻辑：吞吐度量、可持续上限、背压建议、饱和告警
core/app/api/throughput.py
core/tests/test_throughput_engine.py
frontend/src/pages/Throughput.jsx
```

### 数据结构（`engine.py`，无 DB）

- `measure_throughput(runs, *, window_min) -> {platform: {observed, succeeded, failed, success_rate, risk_rate}}`。
- `sustainable_ceiling(capacity, risk_signals) -> {platform: ceiling}`：在 V11 容量基础上，按近期风险率/失败率打折。
- `backpressure_recommendation(observed, ceiling, risk_trend) -> {platform: {action, factor, reasons}}`：`action ∈ {scale_up, hold, throttle, pause}`；**风险上升时只输出 hold/throttle/pause**，`scale_up` 仅在低利用率且风险平稳时给出，且 `factor<=1` 永不建议突破 `ceiling`。
- `saturation_alerts(observed, ceiling) -> list[str]`：利用率超阈值的平台。

### API（`/api/throughput`，只读）

- `GET /overview`：实际 vs 可持续、利用率。
- `GET /backpressure`：每平台背压建议 + 饱和告警。
- 零写、纯聚合。

### 安全边界

背压**只朝降速方向起作用**（`throttle/pause` 永远合法且优先于 `scale_up`）；与熔断器一致地强化（而非绕过）限速；建议仅供人工参考，不自动改变任何执行。

### 验收标准

- 构造「风险率上升 + 高利用率」样本，`backpressure_recommendation` 必给 `throttle` 或 `pause`，绝不 `scale_up`；低利用率且风险平稳时才可能 `scale_up`，且不超 `ceiling`。

## 工程节奏与安全回归

1. 每版本遵循既定模式：纯逻辑模块（`engine.py`，无 DB）→ 单元测试 → 薄只读 API → 幂等 schema（仅 V12）→ 前端页面 → `docs/` 实施记录 + Obsidian 同步 + Git 提交。
2. 依赖顺序：V12 复用 V10/V11；V13 复用 V11/V12 —— 建议按 V10 → V11 → V12 → V13 顺序落地。
3. 新增安全不变量回归（在既有 200 项之上）：每版本至少 1 个直接测试覆盖其安全方向——
   - V10：`respects_rate_limit` 对生成计划恒为真（排程不越限）。
   - V11：`isolation_violations` 能发现共享、正常样本为空（隔离不变量）。
   - V12：未爬坡目标进入 real 波次被 `validate_campaign` 拒绝（爬坡不可跳级）。
   - V13：风险上升场景只产出降速建议（背压单向）。
